# Acceptance of the releases

Every release of the [ledger](../FEATURES.md) has criteria that all have to hold. This page records, for each release, how each criterion is proven and where to look, and what the proof does **not** cover. A criterion without a test or a CI job that can fail is not proven.

| Criterion | Proof | Where |
| --- | --- | --- |

### What this does not cover

- **Other machines than the CI images and the development machine.** The fidelity tests ran on the two Ubuntu images of GitHub (kernels 6.8 and 7.0, iproute2 5.15 and 6.1 with a newer `tc` built for the seed) and on Debian 13 (kernel 6.12). A virtual machine with a busy host may show more noise; the bounds leave room only where the noise can only go one way ([FIDELITY.md](FIDELITY.md)).
- **The wheel on the Arm runner** is built and installed into a clean environment and runs a scenario there, but the fidelity cases run on x86_64 only.
- **Containers, other CI systems, Fedora, Arch, Alpine.** [PERMISSIONS.md](PERMISSIONS.md) says what is measured and what is not.
- **Platforms of the release.** Only Linux has wheels and a backend; the candidates were installed and run on one machine (Debian 13, x86_64) by the maintainer. The Arm wheel is installed and run only by the CI.
- **What a person would call "complete".** The ledger lists what 0.1 contains; the README says what it does not do yet. Round trip time, your own program as a node, a timeline, bursty loss and reports are later releases.

## Release 0.2 "Time and noise"

| Criterion | Proof | Where |
| --- | --- | --- |
| A scenario with a bandwidth drop and an outage produces a time series | A scenario with a rate that drops from 4 to 1.2 mbit and back and an outage of two seconds is run for 14 s, and the series by second has to show all of it in both views (what was sent and what arrived): the throughput of the slow seconds and the delay of the packets that wait in the queue, nothing lost in the drop, no arrival in the outage, the lost packets in the seconds in which they were sent and not where the silence is, the sums of the bins equal to the statistics, and the time to recover read from the bins (0 s seen from the sender and 3 s seen from the receiver after the drop). Every step is recorded with how late it was. The same scene runs from Python as an example with the same bounds | [`timeline.rs`](../crates/netscenario-backend-kernel/tests/timeline.rs): `the_series_of_a_drop_in_bandwidth_and_an_outage_shows_both_in_both_views_and_the_recovery_is_read_from_it`; [`series.rs`](../crates/netscenario-core/src/series.rs), [`recovery.rs`](../crates/netscenario-core/src/recovery.rs); [`scenarios/bandwidth-drop-and-outage.yaml`](../scenarios/bandwidth-drop-and-outage.yaml); [`examples/timeline/`](../examples/timeline/) |
| An assertion with a confidence interval is stable over 100 CI runs | The acceptance test runs a scenario eight times with derived seeds and asserts on the upper end of the interval of the loss, as a user would, and a canary shows that a claim that is false for the link fails. The bounds are derived from the exact binomial tails (the stable claim fails with a probability of 6.6e-11 per call). The workflow `stability.yml` runs the test 100 times, each with a new seed, once a week and on request. The test also runs once in every `just py-check` | [`test_acceptance.py`](../python/netscenario/tests/test_acceptance.py), [`stability.yml`](../.github/workflows/stability.yml), [STATISTICS.md](STATISTICS.md) |
| The documentation is complete for everything in 0.2, the ledger and the coverage matrix are up to date, and each check mark has a test | Every feature with the release 0.2 in the ledger is `done` with a link to what proves it (TOP-07 was split: nodes joining and leaving are TOP-10, 0.6). The test of the Kernel backend that compares the declaration with the matrix, and that every faithful mark links to a file that exists, passes. The format of the scenario, the result, the set of runs, the statistics, the programs, the reports, the Python package and the plugin each have a page, and every decision of the release (D-038 to D-077) is in [DECISIONS.md](DECISIONS.md) | [`coverage.rs`](../crates/netscenario-backend-kernel/tests/coverage.rs), [FEATURES.md](../FEATURES.md), [COVERAGE.md](COVERAGE.md) |
| The new parsers of input that is not trusted are fuzzed | Eight targets (the scenario, the values, a datagram, a file of records, a result file, the lines of metrics of a program, the file of a set, the reports of a result) run every week with a canary that shows that a crash is found | [fuzz/](../fuzz/), [`fuzz.yml`](../.github/workflows/fuzz.yml) |
| Tag, release, announcement | The release workflow ran for a candidate (`0.2.0-rc.1`, 2026-11-03) through all checks, both approvals and the publishing: the five crates and the two Python packages are on the registries, and the GitHub release carries the four files and the attestation of their provenance (`provenance.intoto.jsonl`, the first release that has one) | [RELEASING.md](RELEASING.md) |

**The first full run of the 100 rounds** (workflow `stability.yml`, started by hand, recorded on 2026-11-03): **0 of 100 rounds failed**. Runner image `ubuntu-24.04` (`ubuntu-24.04-x86_64-1`, runner version 2.338.2). A round (the two tests of the file) took about 32 seconds, the 100 rounds about 55 minutes. Every round drew a new seed, so the stable claim held for 100 different sets of eight runs and the canary failed its false claim every time.

### What this does not cover

- **Other machines than the CI images.** The fidelity tests of 0.1 and the tests of the timeline ran on the two Ubuntu images of GitHub and on Debian 13. A machine with a busy neighbour can change the delays of a whole set; the acceptance test asserts on the loss, which the seed fixes and the load of the machine does not move.
- **The coverage of the interval for few runs of a skewed metric** is below the level, and is measured and stated in [STATISTICS.md](STATISTICS.md): the interval is a rough one for five runs of a high delay percentile.
- **A replay on another machine** can lose other packets, because the lost packets of a seed depend on the kernel's `netem` and on `tc`; the replay says so and names what differs ([CLI.md](CLI.md#replay)).
- **Programs of your own** are tested with scripts, Python and a compiled program in real namespaces; the signal of `shutdown` goes to the process group of the program, so a child that the program moves out of its group is not reached by it and is ended only when the run ends and its namespaces go ([PROGRAMS.md](PROGRAMS.md)).
- **Reports** are made from the files of a result directory; the HTML was looked at in Chromium in both colour schemes, which is not a test on every browser.
- **Platforms of the release.** As for 0.1: Linux only, wheels for x86_64 and aarch64. The Arm wheel is installed and run only by the CI.
