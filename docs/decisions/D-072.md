# D-072: A program of your own is started in order, waited for, watched, stopped as a group, and reported with its output and metrics

Accepted (2026-11-02). Closes WRK-06, WRK-10 and PRB-08 on the Kernel backend. D-041 and D-051 settled the format and the ideas; these are the decisions made while building it. `docs/PROGRAMS.md` says what the run does.

- **One pull request, and `on-exit` per program** (the maintainer's choice). `on-exit: continue` (default) lets the run go on when a program ends by itself with an error and reports it; `fail` stops the run with an error naming the program, with the end of its standard error. A crash under a bad network is a finding, so `continue` is the default. This adds a field to `Command`, which becomes `non_exhaustive` with `Command::new`: a real break, so `feat!`.
- **Start in the order of the file, each when the one before is ready; the other workloads after all of them.** A server must be there before the packets. A program that is not ready in time, ends first, or is not found fails the run before any packet. The existence of the file is checked before the start, because `nsenter` would answer with the exit code 127, which says nothing to a person who misspelled a name.
- **The backend gets what a program needs, in the interface and not in the Kernel backend alone:** `Program` has environment, directory, a process group of its own and two log files; `Backend::signal_program` (to the group) and `Backend::port_bound` (the sockets of a node); both default to an error, so another backend says what it cannot do. `ProgramState` has `OutputStats`. The Kernel backend reads the sockets from `/proc/<holder>/net/{udp,udp6,tcp,tcp6}` (S14) and ignores the loopback, which the other node cannot reach.
- **Output is read by the supervisor, to the end, whatever the program does.** The first megabyte of each stream goes to a file, the rest is read and counted, a line of standard output is cut at 64 KiB (S14 saw 2 GB held by a line without a line feed), and at most 10,000 lines wait for the next look. Every drop is counted in the result and warned about in the summary. Alternative: the run writes the files from the polled lines; it would lose standard error beyond its 16 KiB tail and the order of the two streams.
- **Metrics:** a line that starts with `{` and has the key `metric`, with `metric`, `value` and optional `unit` and **no other key**; a line that looks like one and is not valid is counted and the first five are kept with the reason, never swallowed. The time of a reading is the time the run read the line (within 50 ms of the write), not a time that the program claims: the clocks of the program and the run are not compared. A summary in `result.json` and every reading in `metrics-<id>.jsonl` (the shape of D-070). The exit code is not a metric.
- **Stop:** after the settle, the signal of `shutdown` to the process group, `KILL` after `within`, `ended` says `on-its-own`, `stopped` or `killed`. A program started in a group of its own is the only way to reach its children (S14). On any error the groups are killed before the network is torn down.
- **The supervisor resets its signals first.** On Ubuntu 22.04 the `unshare` of util-linux 2.37 starts the first process of a pid namespace with `SIGTERM` and `SIGINT` ignored (checked in a container: `SigIgn 0x4002`), and an ignored signal stays ignored across `exec`, so no program could be stopped by `TERM`; the first CI run showed every program `killed`. The supervisor installs a handler for the six signals a `shutdown` can send (`signal-hook`, safe), and `exec` resets a handler to the default. A test starts the supervisor through a wrapper that ignores `TERM` and `INT`, which fails without the reset.
- **What the run cannot count:** a program sends packets that the run neither counts nor orders. The tally of the directions and the check of the queues are left out for such a scenario, and a link direction that the program may send into and whose queue draws random numbers gives `loss_reproducible: false` with the reason (D-065 for programs).
- **Tested:** unit tests for the substitution, the variables and the search for the program; the metrics parser and collector (every way to be wrong); the readers of the output (long lines, the limit of the file, lines past the limit); the table of sockets. In real namespaces (`command.rs`, and `programs.rs` for the backend alone): the environment, directory and group of a script; every way of being ready, in order, with a compiled program (the agent), Python and sh; late, early end and missing program; a program that ignores `TERM` is killed with its child; crash with both `on-exit` values; three megabytes of output; a program next to a stream; a cancel. The Python test runs a script through `ns.run`, and `examples/echo-server` is a pytest test of a server and a client over a link with loss.

Alternatives: a shell string for `run` (D-051); the program's own timestamps in metrics (clocks to compare); a metric format with labels or histograms (later, if wanted); `on-exit` as a run-wide option (a client may be meant to end, a server not).
