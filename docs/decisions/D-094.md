# D-094: `expect` in the file: a list of named checks on the metrics of a run or of a set of runs, judged by the core

Accepted (2026-11-10), for ASR-07. The assertions of release 0.1 are plain `assert` in test code on the numbers of the result; this is the same claim written in the scenario file, so that the file says what it must show and `netscenario run` can judge it without a test framework.

- **The shape.** `expect:` is a mapping with an optional `repetitions` and the list `checks`. A check has an optional `name`, the `metric` (a name of [STATISTICS.md](../STATISTICS.md), `media.delay.p99`), and one or more statistics, each with a bound written as a string: an operator (`<`, `<=`, `>`, `>=`) and a value in the unit of the metric (`"< 150ms"`, `">= 97%"`, `"<= 0"`, `">= 8mbit"`). A bound is an expression-friendly string, so `"< {rtt * 3}"` works (D-093). The statistics of one run: `value`. The statistics of a set of runs: `mean`, `median`, `min`, `max`, and `ci95-low` and `ci95-high`, the ends of the 95 % interval around the mean (D-074). A check with two statistics is two lines in the verdict.
- **One run or a set, never both.** Without `repetitions` the file is judged by one run and its checks use `value`. With `repetitions: n` (5 to 1,000, the bounds of a set) the file is judged by a set and its checks use the statistics of a set. A file that mixes the two is refused when it is read. `repetitions` here is what the claim needs, not an option of the run that would leave the scenario unchanged: `netscenario run file.yaml` makes that many runs, `--repetitions` may ask for more and never for fewer (a claim about the interval of 20 runs is not judged by 10), and a file that judges one run is refused by `--repetitions` with the reason. It is in the file, and so in the hash, because the claim is in the file.
- **The unit decides what a bound may be.** The metric must exist for the scenario (its workload is there, an `echo` metric needs `echo: true`, a TCP metric needs a TCP workload), with a hint when a name is close; a program's own metrics (`<program>.<name>.last|min|max`) are numbers in the unit of the program. A delay takes a duration, a rate a rate, a ratio a percentage or a number from 0 to 1, a count a number. The bound is compared as the metric is stored (seconds, bits per second), with the exact value of what was written.
- **Judged in the core, recorded in the result.** A run (`result.json`) or a set (`runset.json`) has `expect` when the file has checks: for each check and statistic the bound as written, the value, the margin (how far on the good side of the bound, negative when it failed), whether it held, and a note when it could not be judged. A check on a metric that the run does not have (no packet arrived, so there is no delay) **fails** with that note and is never skipped: a claim that cannot be checked is not a claim that holds. In a set, a metric that only some runs have fails the same way. A run that was interrupted is not judged. The reports read the verdict from the directory, so they stay a function of the directory.
- **What the user sees.** `netscenario run` prints the checks and exits with 1 when one failed (the code that CLI.md has kept for this), the Markdown and HTML reports show each check with its value and margin, the JUnit report has one test case for each check with the failure message, and Python has `Result.expect` and `RunSet.expect`. The pytest plugin fails a test that runs a file when a check of the file failed.
- **The interval is that of the default set.** `ci95-*` are the 95 % bootstrap interval around the mean. A set that was asked for another statistic or level (library and Python only) is refused when the file has checks, because the key would say something the interval is not.
- **Not in this decision**: a comparison with a baseline or another set (ASR-04, ASR-05), checks on the series, the time to recover or a phase of the run, conditions between checks, and a bound that is a function of another metric.

Alternatives: a list directly under `expect` as the first sketch had (no place for the repetitions that the claim needs, and the number would be an option on the command line that a file cannot require); the operator as a key (`"<": 150ms`, which says nothing about the statistic and cannot hold two bounds on one metric); a statistic per check and a list of bounds (longer, and the common case has one); judging in the reports (the exit code of `run` and the plugin would need a second judge, and two judges drift); skipping a check whose metric is absent (a stream that lost every packet would pass `delay.p99 < 150ms`).
