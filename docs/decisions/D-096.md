# D-096: A change from test code is a step of the timeline made at a hold of the sender, on a link that was declared live, and the async API is the same run handle

Accepted (2026-11-10), for TML-05 and PYT-04. A test wants to change a link at a moment it chooses ("when the app has connected, drop the rate") and to run a scenario from `asyncio` code without blocking the loop. Both need a run that can be talked to while it goes. This decides what that is, so that a live run stays honest about what it measured.

- **One handle for both.** The run stays one blocking call (`run` in Rust, `netscenario.run` in Python). Next to it comes a way to talk to a run that is going: in Rust a `LiveHandle` (cloneable, `Send`) with the inbox that `RunOptions::with_live` hands to the run; in Python `netscenario.start(scenario, live=("access",))`, which starts the run on a worker thread and returns a `Run` (a context manager) with `run.link("access").set(...)`, `.down()`, `.up()`, `run.elapsed`, `run.events`, `run.result()` and `run.cancel()`. The async API wraps the same object: `await netscenario.run_async(...)`, `async with netscenario.start_async(...) as run`, `await run.link(...).set(...)`, `async for event in run.events()`. There is one implementation of "a run that can be talked to", not two.
- **A live change is a step, recorded like any other.** The caller gives the same edit as a `set` of the file (`delay`, `loss`, `rate`, a `model`, ...; `forward`, `reverse` or `both`), or `down` or `up`. The core turns it into the steps that the file would give, appends them to the run's list, does them, and returns the record (`events`, with `live: true`) to the caller once the backend has applied them. The edit is applied to the state the direction is in at that moment, planned steps and earlier live steps included, so that the state is what a file with all these events would give.
- **At the packet, not at the clock.** The caller's moment cannot be planned, so the sender cannot have a barrier for it from the start. The run asks the sender to **hold** (`hold <id>` on its standard input, next to `go` and `stop`); the sender looks for the request before every packet, answers with the `barrier` line it already has (with the number of the next packet), and waits for `go <id>` as for any barrier. The step is done between two packets, the number of the packet that met the old state is known exactly, and `held_ns` says how long that packet waited (a change takes 0.2 to 0.5 ms, D-063). The sender is the first workload that sends into the direction, as in D-062. A direction no workload sends into, or after the last packet, is done by the clock and says so (`packet` is empty), as a planned step there.
- **A run with live changes replays exactly, and is not promised to repeat by itself.** The moment is the test's, so two live runs differ. What the run records is the scenario **with the live steps as events at the moment of the packet slot** they were done at (the time of that packet in the schedule of the sender, so the plan binds the same packet again), and the list of live links. `replay` reads that, and a replay gives the same lost packets as the run did, as for any scenario. `seed.loss_reproducible` of the live run itself is `false` with the reason "a change was made from test code" when a live step changes what a direction draws random numbers for. Not taken: recording only the wall time (a replay would land before a different packet).
- **A link is declared live before the run.** The layout of the queues of a direction is made from every state it goes through and does not change (D-059): rebuilding drops the packets in flight and starts the generator again. A change from test code names no state in advance, so the links that may be changed are named when the run is started (`live=`, `RunOptions::with_live_links`), and the backend builds for them the layout that fits any state: two queues, a seed, a rate stage that passes on at once while no rate is set. A live change of another link is refused with a message that names the link and the call. Not taken: rebuilding on a live change (D-059 says why not), and a key in the file (the file describes the network; which links the test code touches is a fact of the test, and the result records it so a replay builds the same layout).
- **What cannot change live is refused, before anything is touched.** The check that a backend runs over a timeline (`timeline_refusals`: the jitter distribution cannot go back, D-059; the longest limit is fixed by the layout; the features a backend lacks) is run over the file plus the live steps so far plus the new one, and a refusal is an error to the caller naming the step, the feature and the backend. A backend without live changes (the Engine backend, whenever it exists) refuses `live=` at the start, not at the first change.
- **How it is built (as done).** The links come from the options of the run and travel with the scenario in memory (`Scenario::live_links`, not part of the file, never hashed); `timeline::states_of` adds one state for such a link, with a delay, a rate, loss, reordering, duplication and corruption all on, and no jitter of its own (the distribution of a jitter is fixed by the first one a queue gets, D-059, and the code must be free to choose it; a link that starts with a jitter keeps that one). Every consumer of `states_of` (the layout in the backend, the accounting of the run, the check for a refused feature) then sees a link that can be in any state, and nothing else changed. The steps of the timeline carry the edit that made them (`Step::edit`), and the loop works the state of a direction out from the state it is in when a live change has touched it (`drive::Tracker`), so a step of the file that comes after a live change keeps what the code set, as the replay (which works all the steps out in order) does. A request is checked against the file plus the live steps done so far plus the new one, with the checks of the start (`check`, `check_values`), before the sender is asked to hold.
- **The record.** A live step is an `events` entry with `live: true` (`event` is its place among the live changes, `scheduled_ns` the moment the code asked) and its event goes into the recorded scenario at the slot of its packet; the hash in the result is the one of that scenario. If two packets leave at one moment, so that the slot does not bind to the packet again, the result says so in `notes`.
- **Python threads and `asyncio`.** The worker thread is joined on every path (leaving the `with`, an exception, `cancel()`, cancelling the task); `run_async` shields the wait for the thread, so a cancelled task ends only when the network is torn down. Events go to the loop with `call_soon_threadsafe` into a queue; there is no dependency on a plugin for tests (`asyncio.run`) and none in the package.
- **Frames.** `to_pandas()` and `to_polars()` on the records, series and events are optional extras (`netscenario[pandas]`, `[polars]`); the package imports neither unless the method is called, and the error when it is missing names the extra.

Alternatives: a timeline thread next to the loop (D-060: the backend is single threaded); the clock for a live step (cheaper, and the replay would not be exact); a layout rebuilt on a change (D-059); a `live` key in the file (see above); a separate async implementation with its own run loop (two ways to be wrong).
