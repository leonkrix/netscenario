# D-073: What is measured is in the scenario, an option of a run replaces a key, and a capture takes both ends of a link

Accepted (2026-11-02). Closes PRB-09 on the Kernel backend. D-047 settled the method of the capture; D-070 had put the bin and the definition of the time to recover among the options of a run. This decision moves them, because the capture would have been the third setting in the wrong place.

- **One rule: the file says what runs and what is measured; the options of a run say how this machine runs it** (the maintainer's choice). A threshold on the time to recover (`expect`, later) only means something next to the definition of the time to recover, a result must say how it was measured, and the hash of the scenario tells whether two results are comparable. A bin of 1 s and a bin of 100 ms give different recovery times; with the bin in a command line the same file could give two numbers. The section is `measure`: `series.bin`, `recovery.{basis, baseline-bins, window-bins, fraction}`, `capture` (link ids) and `packets`. What stays an option: the directory of the result, the seed to repeat a run with, the settle time, the working directory of the programs, the form of the output (`--json`).
- **An option with the name of a key replaces the key for one run** (`--bin`, `--recovery-*`, `--capture`, `--packets`; the same names in Python and in the marker). It is applied to the scenario before the run, the scenario is checked again (an override can be as wrong as a key, and the error names the key), and the result records the scenario as it ran, so its hash is the hash of what was measured. `--capture` replaces the list, it does not add to it, because "also this one" has to be said by listing both. `RunOptions` loses `bin`, `recovery` and `export_packets`; `MeasureOverrides` and `Measure::apply` replace them. This is a break of the library and of the Python signature of 0.1 (the options of the series are 0.2 only, but the three exist in a release), so `feat!`.
- **`probes` was reserved for "extra measurements" and `measure` is that.** The reserved key is removed so that nobody is told that a key is planned that never arrives; `probes` is now an unknown key.
- **Both ends of each captured link**, `capture-<link>-<node>.pcap` (the maintainer's choice). The tap sits after the queue, so the two files differ in exactly what the link did between them, and a test can compare them. One end would have needed a rule for which end, and the answer to "what did the link do to this packet" needs both.
- **The capture starts before any program and any sender and stops after the last program**, so a request that a program sends while it starts is in the file, and the last answers are too. Names: the interface is `l<link>` in both nodes (`Backend::interface_name`, default an error, so another backend says what it cannot do).
- **Timestamps are the kernel's, on the real-time clock, with the offset in the result.** A pcap has wall-clock time by convention and the tools that read it assume that; the result gives `realtime_minus_monotonic_ns` taken at the start, so a frame can be placed on the monotonic clock of the records (`t - offset`). The test matches each frame at the receiving end with the record of the same packet by its sequence number and demands that it was stamped after the sender sent it plus the delay of the link and before the receiver read it, to within a millisecond for the offset.
- **It checks itself.** The agent reads `/proc/net/dev` before and after and compares the frames the interface counted with the frames in the file: `missing` is the difference, `null` if the counters could not be read, and the summary warns in both cases. A buffer that overflows is therefore never silent. The test makes it overflow on purpose (the capture is stopped with `SIGSTOP` while traffic flows and continued) and demands the exact count.
- **The agent writes the file.** A new subcommand `capture` in the agent, with `nix` for the raw socket (no `unsafe` in our code, D-047); the supervisor starts it in the namespace of the node like the other agents and reads its summary from the event stream. `tcpdump` as a program would be a tool the machine may not have, in a version that cannot run in a user namespace on Ubuntu 22.04 (D-047).
- **Tested:** unit tests for the pcap writer and reader (the header `tcpdump` reads, frames back to the nanosecond, a file cut short wherever it is cut, a file of another kind named as such) and for the overrides (what is replaced and what stays); the corpus of faulty files (eight files, one fault each); in real namespaces (`capture.rs`): both ends read by `tcpdump` and by our own reader with the same count, a link with loss and duplication (the lost are in no file, the duplicates twice, the same bytes at both ends), the timestamps monotonic and consistent with the records of the same packets, a capture cut short refused (canary), and a buffer that overflows reported against the counter of the interface. In Python: the builder, the result class with its canaries, a real run by file and by argument, and the marker.

Alternatives: keep the options of the series in the run and add only `capture` to the file (two places for what is measured, and a result that cannot say how it was measured); put everything in the run (a scenario that is not the whole experiment, and no way for `expect` to be next to what it judges); capture one end by default (see above); `tcpdump` or `dumpcap` as a program (above); a ring buffer for a capture beyond 100,000 packets per second (`unsafe`, a crate of its own; the stream of a test is a few hundred packets per second and a loss is always detected).
