# D-081: The IP family is chosen for the network and for the workload, a link has one MTU, and what fragments is accounted for by frames

Accepted (2026-11-04). Release 0.3 adds IPv6 (TOP-08) and the MTU of a link with the fragmentation it causes (LNK-10).

- **The family is a property of the network and a choice of the workload.** `topology: { ip: v4 | v6 | dual }` (default `v4`) says which addresses the network gets and whether IPv6 is switched on in the nodes; `ip: v4 | v6` on a workload picks the family of that flow (default: the only family of the network, `v4` in a dual-stack network). A workload that asks for a family the network does not have is refused before the build. The key must be on the network because IPv6 in a namespace is not quiet (a few packets in the first second, S16): a v4-only network keeps it off, as now, so that the seeded loss does not move.
- **Addresses.** IPv4 as before (`10.100.n.0/30` on the links, `10.200.0.<index+1>/32` on the loopback of a node). IPv6: `fd00:100:<n>::/126` on the links, `fd00:200::<index+1>/128` on the loopback; unique-local addresses, no router advertisements, no duplicate address detection, fixed neighbours, so that the namespaces stay quiet. A dual-stack network has both. `{node.addr}` is the address of the node in its family (v4 where the network has it).
- **A network with IPv6 waits one second before the queues are built.** The interfaces send a few packets of their own when they come up (neighbour discovery, multicast listener reports); the wait lets them pass before the first queue exists, so that the queue counts only the packets of the workloads.
- **The UDP checksum cannot be switched off over IPv6** (the protocol requires it): a workload with `ip: v6` and `udp-checksum: false` is refused with that reason and the advice to use IPv4 for the test.
- **One MTU for a link, not for a direction.** `mtu` on a link sets the interface at both ends; the kernel refuses a frame that is longer than the MTU of the interface that receives it, so two different MTUs would not give a direction of its own but a link that drops. 68 to 65535 (IPv4), 1280 or more where the network has IPv6.
- **Fragmentation is accounted for by frames, and a router never fragments.** A datagram that does not fit the first link is cut by the sender into `n` frames (IPv4: fragments of `(mtu - 20) / 8 * 8` bytes; IPv6: the same with the fragment header), and every later link carries those frames whole, so its MTU must be at least that of the first. A datagram that fits the first link but not a later one would be cut (IPv4) or dropped with an ICMP error (IPv6) by a router, in sizes the run cannot account for, so such a scenario is refused with the sizes. A queue sees frames: its count is `n` times the packets sent. A frame lost in a queue loses the datagram (`1 - (1 - p)^n`), which the fidelity case checks. The tally of a link (D-040) is by datagram, so a workload with `n > 1` has none; its queue is still checked, by frames. `dont-fragment: true` on a workload makes the sender refuse a datagram that does not fit (counted like a refused send).
- Alternatives: `ip` on the workload alone (IPv6 would have to be on in every node of every run, or the namespace is not quiet); an MTU per direction (not possible on a veth pair, see above); let routers fragment and count the frames afterwards from the kernel (no per-flow number, the check of the seeded queues would be lost).
