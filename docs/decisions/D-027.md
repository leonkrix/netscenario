# D-027: The result format of release 0.1, how a run is ordered, and what the statistics mean

Accepted. The format is described field by field in [RESULTS.md](../RESULTS.md).

- **One directory, one JSON result, raw records beside it.** `result.json` (versioned: `format` and `version`, 0 until 1.0), the binary records of each workload (D-025), and on request one JSON Lines file with a line for each packet. The result holds everything a reader needs to judge it: the provenance (version of netscenario, time, backend and its details, kernel, processor), the seed with `drawn` and `loss_reproducible`, the accepted restrictions, the addresses and a fingerprint of the scenario. No host name, user name or path, because a result may be shared.
- **The fingerprint is SHA-256 of the canonical JSON of the scenario**, so comments and layout of the file do not matter and any value does. SHA-256 is written out in the crate (forty lines, the published test vectors, a million-letter case), not taken from `sha2`: a fingerprint protects nothing, and one dependency less is worth more than the convenience. The tests pin the output, so the crate can replace it at any time.
- **The order of a run** (`netscenario_core::run`): provision, start every receiver and wait for `ready`, fix one moment 500 ms ahead and start every sender with it (so the workloads start together and a slow start of a process does not shift one of them), wait for the senders, wait the `settle` time for the packets in the network, tell the receivers to stop, read the records, tear down, compute and write. The network is torn down on every path, and the first error is the one returned. A workload with `start` and `stop` is a sender with a later moment and a shorter duration.
- **`settle` was a fixed wait, not a drain detection** (the default is measured since D-067; this is the reason for the fixed one that remains for a backend that cannot count). A receiver cannot tell a packet that was lost from one that is still in the network, so the run waits one second plus twice the longest hold of the scenario (largest delay plus four times the largest jitter). A packet that needs longer counts as lost, and the result says how long the run waited (`timing.settle_ns`). A rate limit that builds a queue longer than that is not covered by the default; the `settle` option exists (open: the command line, and a default that knows the queue).
- **Statistics are plain and stated exactly.** Loss is `lost / sent` with `lost = sent - distinct packets that arrived`. Delay percentiles are the nearest rank (always a measured delay). Throughput is the payload that arrived in each second, counted from the first packet sent, not scaled. A duplicate counts once and not in the delays; a sequence number that was never sent is counted as `unexpected` and not as received. Each rule has a test with numbers worked out by hand, and canaries that fail on wrong data.
- **The backend tells the run its addresses and itself.** Two methods of the interface: `address(link, end)` (the Kernel backend computes `10.100.n.1/.2` on the caller's side, with the function the supervisor uses) and `describe()` (name and details such as the version of `tc` and how the rights were obtained).
- **The tests of the run are of two kinds.** With a fake backend that plays the agent: order, arguments, failure paths and the teardown on each. In real namespaces with the real agent: the delay of the link, a window of a workload, two workloads in opposite directions, the loss pattern of a seed (same seed, same lost packets, another seed other ones) and a run that cannot start.
- **Not in this change:** the command `netscenario run` and `validate` (CLI-01), which find the agent next to the program (`agent_next_to`) and the supervisor in the same program; round trip time (PRB-03); reordering (PRB-04).

Alternatives: a JSON result with all packets inside (too large), CSV (no types, no versions), a hash from the `sha2` crate, a drain detection by watching the receiver go idle (cannot tell idle from lost, and a slow queue looks idle), starting the senders one after the other as soon as each is ready (the workloads would not start together).
