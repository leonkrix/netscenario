# D-034: A release is a tag; one version for everything; the registries trust the workflow, and a maintainer approves

Accepted. The steps are in [RELEASING.md](../RELEASING.md), the promises in [VERSIONING.md](../VERSIONING.md).

- **One version for the five crates, the two Python packages and the programs in the wheel** (D-004). It is written once, in `Cargo.toml`; `python/release/version.py` writes the other places (the internal dependencies, the plugin and its exact pin on `netscenario`) and checks all of them, the lock files included, in the tests and in the release workflow. A pre-release is `0.1.0-rc.1` for Cargo and `0.1.0rc1` for Python; the script converts, and the release checks the names of the files. The plugin depends on exactly the same version, so a plugin never meets another package than the one it was tested with.
- **Five crates are published, the bindings are not.** `netscenario-model`, `-core`, `-backend-kernel`, `-agent` and `-cli` go to crates.io under their names (the command is still `netscenario`, `cargo install netscenario-cli netscenario-agent`); `netscenario-py` is `publish = false`, because it exists as the wheels. Every package carries the licence texts (copies, checked by a test) and the README of the repository. `cargo publish --workspace` orders the crates and builds each against the packages of the others; the CI does it as a dry run in every pull request.
- **The release is made from a tag, not from a branch.** The tag must be on `main`, name the version in the files, have a section in `CHANGELOG.md`, and its commit must have passed `CI passed`. The jobs then repeat nothing that the CI tested differently: the wheels come from the same reusable workflow (`wheels.yml`) that the CI calls, so what is published was built and installed the way the CI did.
- **No stored token.** crates.io and PyPI trust this workflow, each in an environment of its own (`crates-io` and `pypi`; trusted publishing, OIDC), so the job for one registry cannot ask for the token of the other; the PyPI upload makes attestations (PEP 740) for every file. The environments have the maintainer as a required reviewer, so nothing is published before a person looks at the finished run: there is no staging on either registry, and the approval is the staging. The two publishing jobs each need it, so the crates (immutable, cannot be undone) and the packages on PyPI are two decisions. The deployments link to the pages of the published versions. The publishing jobs use no cache and no artifact except the checked one.
- **The changelog is the titles of the pull requests** (Conventional Commits, squash merge), by git-cliff, written into the release pull request, where a person reads and edits it before it is merged. A title that is not conventional is shown under "Other", never dropped silently. The commits of the experiments before the workspace are left out.
- **Before 1.0 a minor release may break**, in the open: the title has `!`, the changelog says **Breaking**. The format versions stay 0 until 1.0.
- **First release by hand for crates.io only**: trusted publishing needs a crate that exists, so the names are taken with `0.0.0` and the versions yanked; PyPI has pending publishers and needs no placeholder. Only one pending publisher can exist for a repository, workflow and environment, so the second new project can be registered only after the first upload of the first; for the first release of this repository that meant a gap between the upload of the wheels and the upload of the plugin, and `0.1.0-rc.1` was published that way (two jobs, three approvals). With both projects in place the upload is one job again, wheels first and then the plugin, because the plugin pins exactly the wheels. The environments were renamed from `release` to `crates-io` and `pypi` after that release, and `0.1.0-rc.2` tested the change.
- **Not in 0.1**: static binaries, musllinux and macOS wheels, a source distribution of `netscenario`, signing of the GitHub release, an SBOM.

Alternatives: `release-plz` or `release-please` (a bot that opens the release pull request; more moving parts and a token that can push, and the review of the changelog is the part that matters), `cargo-release` (a local tool that publishes from the maintainer's machine, which needs a stored token), an API token in a secret (the thing trusted publishing removes), cibuildwheel (D-033).
