# D-103: The run chooses the backend, the scenario does not; the default is the kernel; `auto` picks the one that is faithful and says so

Accepted (2026-11-12), for BKD-14.

- **The run chooses.** `netscenario run --backend kernel|engine|auto`, `backend=` in `run`, `start`, `run_async` and for a set, and an option and a marker of the plugin. The scenario file describes a network and never names the tool that emulates it: the same file runs on both, which is what the comparison of D-102 needs, and a replay uses the backend recorded in the result.
- **The default is `kernel`.** It is the reference (the first principle) and it is what 0.1 to 0.3 users have. Changing the default later is a decision of its own.
- **`auto`** takes the kernel when `doctor` says it can do what the scenario asks faithfully (the modules are there, the rights are there) and the engine otherwise, shows the choice in the output and records it in the result (`provenance.backend` and `provenance.backend_choice`: the requested name, the used name and the reason). It is never silent, and a scenario that neither can do is refused with the reasons of both.
- **The settings of a backend** belong to the run, too: `engine.timer` (D-098), the limits of the queues of the engine, whether the decision log is written. They are recorded in the result and the scenario hash is the same for both backends.
- **A result says what made it.** The version of the engine, its timer, its lateness distribution and its overload flag (ENV-08) are in the provenance; a report prints the backend in its first lines.

Alternatives: a key `backend:` in the file (the file would no longer be one network that two tools run); `auto` as the default (the same file would give different measurements on two machines before anyone asked); no `auto` (a laptop without `netem` would need to know about the engine before it could run anything).
