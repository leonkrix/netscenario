# D-095: A profile is a named set of sourced values for a link, resolved when the file is read and recorded with the version of the library

Accepted (2026-11-10), for SCN-06. A test of a program wants "a link like LTE" without the author having to know what LTE is; the numbers must be real, or the test learns nothing. This decides what a profile is, where it is written, what it may contain and how a run keeps it.

- **A profile sets only what a source says.** A profile has a value for a key (`delay`, `loss`, `rate`, `queue`, a `model`) only if a measurement, a standard or a published report states it, or if it follows from such figures by arithmetic that [PROFILES.md](../PROFILES.md) shows (half of a round trip, a share of a packet count). What no source gives is **not set**, and the author writes it next to the profile. There are no estimates in the library, also not marked ones: an estimate that is marked is still a number that a test will take for a fact. A family, a tier or a key waits for its source and comes with a new version of the library. The first library (version 1) is therefore smaller than the plan of the families; PROFILES.md says what is missing and why.
- **Where it is written.** `profile: <id>` is a key of a **link**, next to `forward`, `reverse` or `both`. Not of a direction: a profile has an up and a down value, and which is which is only known for a link. The first node of `between` is the terminal and the second the network, so `forward` is up. A direction writes its own keys.
- **How it combines.** The link gets `forward` and `reverse` (and a `model`) from the profile, and the keys the file writes win, key by key (a `loss` written next to the profile replaces the `loss` of the profile as a whole, as a step of the timeline does). `both` applies to both directions and wins over the profile in both. A key set to `null` is not an option: a profile cannot be partly taken away; write the keys you want and leave the profile out.
- **Resolved when the file is read, recorded in the scenario.** The profile is replaced by its values in the typed scenario, in the pass where the file is checked, so every loader (CLI, Python, pytest) does the same and the backends never hear of profiles. The link keeps `profile` as the record, and the scenario gets `profile-library: <n>` with the version of the library that was used. A scenario that **has** `profile-library` is not resolved again: its values are what the run used, so `scenario.json`, a replay and a set that reads it are exact even when the library of a later release has other numbers. The canonical form and its hash contain both, so a scenario with another version of a profile is another scenario.
- **The library is data.** One file, `crates/netscenario-model/profiles/library.yaml`, with the version, embedded in the binary: for each profile the id (`family-tier`), the family, the tier, a sentence of what the tier is, the ids of the sources, and `up`, `down` or `both` with the keys of a direction. It is read by the same reader as a scenario, so a number in it is checked like one in a file. The sources are in [PROFILES.md](../PROFILES.md); a test refuses a profile that PROFILES.md does not mention, and one without a source.
- **Tiers are named after what the source measured**, defined in PROFILES.md ("good" is the lowest published median, "poor" the highest of the sources used), not guessed. A tier with one source is a tier of one source.
- **An unknown profile is an error** that names the closest ids and the command that lists them. Changing a number of a profile later is a new version of the library, with a line in the changelog of PROFILES.md; `netscenario profiles` shows the version.
- **The commands.** `netscenario profiles` lists the library (id, family, tier, what it sets), `netscenario profiles <id>` shows one with its values and sources, both with `--json`. `netscenario capabilities` prints what the Kernel backend reproduces on this machine (the feature section of `doctor`), with `--json`.

Alternatives: estimates marked as such (the plan's first draft; rejected by the maintainer: a marked estimate is still read as a figure); a profile in a direction (cannot tell up from down); resolving in the backend or at run time (a replay would take the numbers of a later library, and a scenario would mean different things in different releases); a `profile` that stays unresolved in the canonical form (the same problem, in the hash); a table of profiles in the Rust source (a data change would be a code change, and the file could not be read like a scenario); a family without a source kept with guesses so that the library looks complete.
