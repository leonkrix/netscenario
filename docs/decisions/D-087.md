# D-087: A UDP stream can be echoed, and the round trip is the time from the first send to the arrival of the echo

Accepted (2026-11-06). For PRB-12 on datagrams. D-086 promised it with the TCP workloads and moved it out when the format and the run of TCP were done.

- **A key, not a kind.** `echo: true` on the five UDP kinds (`udp-cbr`, `udp-poisson`, `udp-onoff`, `udp-bursty`, `trace-replay`). The stream is the same; only the far node also sends every packet it recorded back, unchanged, and a receiver in the sending node collects them. Not with `udp-checksum: false` (the echo is an ordinary datagram), which the model refuses.
- **The round trip is measured in the sending node.** The packet carries the time it was first sent, the collector records the time it arrives back, and both are readings of `CLOCK_MONOTONIC` of the one machine, so the difference needs no synchronisation. The result gets `echo` in the entry of the workload with the statistics of the packets that came back: `received` is the number that came back, `lost` the number that did not (on the way there or back), `delay` is the round trip.
- **The echo goes through the reverse direction** and is subject to its delay, jitter, loss and queue. Nothing is added to the way back.
- **The collector for a flow binds the port of the flow in the sending node**, so a node can collect the echo of one flow and receive another without a clash.
- **The run does not account for the echo packet by packet.** Like a program or a TCP workload, the echo puts packets into the queues that the run has not counted from the sender's side: `directions` and the check of the queues are left out for a run with an echo. The counters of the queues are still read.
- **Reproducibility.** The far node sends a packet back when it has read it, in the order it read them, so the packets that reach the queue of the way back are those that survived the way there, in the order of their arrival. The run therefore treats the echo as a flow of its own on the way back: with a random queue there and one echo alone, and a way there that keeps the order, the same seed loses the same packets (a test runs the same file twice and compares the sequence numbers that came back). The existing reasons apply to it: the echo of two streams through one queue, or a way there with a jitter or a reordering, say that the loss may differ from run to run, and name the echo.

Alternatives: a new workload kind `udp-echo` (it would repeat the five kinds' keys); a round trip from the packet capture (needs a capture on and the host's clocks); counting the echo packets in the accounting (the run does not know the reverse path's first-link frames before the far node has read the packets, and a TCP run has the same limit; it stays an open item).
