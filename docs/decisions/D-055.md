# D-055: The Kernel backend applies corruption, and the result accounts for every packet of a direction

Accepted (2026-11-01), on the ground of D-040 and the spike S13b. D-040 stands as revised on 2026-10-31; this entry says what the first half of it became in the code and why it was cut in two.
- **`corrupt P%` is built into the first queue**, with the loss and the rate, and draws from the seed of that queue (a direction with a corruption has a seed, as it does with a loss; the core already counted it as random). In the tree of two queues it stays in the first: it works on the frame as it enters, before the rate and the delay, as in `netem_enqueue`.
- **The account of a direction is read from the receiving node.** `Backend::node_counts` returns the frames that arrived at the interface of the link and the UDP datagrams the node dropped for a full receive buffer; the run reads them before the senders start and after the wait, and the difference is what the run caused. The Kernel backend reads `/proc/<pid>/net/dev` and `/proc/<pid>/net/snmp` of the process that holds the namespace of the node, so no tool is needed and nothing enters the namespace. The result has, for each direction that carried a workload, `sent`, `reached_node`, `delivered`, `lost_in_queue = sent - reached_node` and `dropped_corrupted = reached_node - delivered - receive_buffer_drops` (`docs/RESULTS.md`). In S13b the counter of the interface was exact in every run, and it includes the frames with a damaged destination address, which no other counter sees.
- **A full receive buffer is not corruption.** A datagram that the node drops because the socket buffer is full is also a frame that arrived and was not delivered. Calling it corrupted would put a fault of the receiver into the account of the network, so the UDP counter `RcvbufErrors` is read as well and kept apart (`receive_buffer_drops`). The agent asks for a buffer of 4 MiB, so this is expected to stay 0; the field exists so that the day it is not, the result does not lie.
- **What the account does not claim.** In a direction with `duplicate` the frames include the copies, so `lost_in_queue` is `null` there (`dropped_corrupted` is still exact: the copies are delivered or dropped like the packets); the same for a direction that received more frames than were sent. A scenario with a program of your own has no account at all: the agent does not count what a program sends, and an account that does not add up is worse than none. The account holds for all the workloads of a direction together; it does not name the packets.
- **The share that is dropped is less than `P`, by a known amount.** `netem` flips one bit of one byte of the whole frame, the Ethernet header included (S13b); the node drops the frame unless the bit is in the source address of the Ethernet header (6 of the bytes). So 10 % corruption drops `10 % x (frame - 6) / frame`: 9.43 % at 64 bytes of payload, 9.75 % at 200, 9.95 % at 1,200. Measured on 40,000 packets each: 9.45, 9.87 and 10.06 %. The fidelity cases 15 to 17 judge exactly this number, case 18 a corruption together with a loss (the loss comes first and the corruption works on what is left), and the canaries run a corruption that is missing and a loss of the same size in its place: the program sees the same loss in both, only the account tells them apart, and the case fails for it.
- **Corruption is not reproducible by the seed, and the result says so.** The seed fixes which packets `netem` chooses for corruption (it draws that from its own generator, which the seed sets), but not the byte and the bit that it flips: `netem` takes these from `get_random_u32_below`, the generator of the kernel. A flip in the source address of the Ethernet header (6 of the frame's bytes) harms nothing, so a corrupted packet now and then arrives in one run and is dropped in another. The first version of the run test claimed the opposite, passed once on a laptop, and failed on all three runners; eight runs of the same seed on the laptop then showed one packet in one of them that differed (later, with a model: each corrupted packet is harmless with a chance of 6 in the length of the frame, so with 41 packets of 1,200 bytes two runs differ by one packet a third of the time and by four or more once in 1,500 pairs; 5 of 12 measured pairs differed, by one; the CI saw a difference of four once, which that tail allows). So `loss_reproducible` is `false` for a scenario with corruption, with the reason in the new `not_reproducible_because` of the result (it also carries the two reasons that the command line used to work out itself); `lost_in_queue` repeats exactly. Not taken: calling it reproducible with a note (a field that says `true` must be true), and a correction in the backend (the place of the flip is not ours to set).
- **A defect found on the way, and fixed.** The check of the queue (ENV-07) subtracted the packets the kernel refused from the packets the sender counted, but the sender counts only the packets it handed over, so a run with refused packets would have been called not reproducible by mistake. A test with a sender that had two refusals fails without the fix.
- **Why it is a first half.** D-040 also asks for `udp-checksum: off` (a corrupted payload that arrives, found by a CRC-32 in the wire format, version 2) and for the sequence numbers of the corrupted packets (a raw socket in the receiving agent, which shares its code with the capture of packets, D-047). Both are separate pieces with their own wire format, model key and fidelity cases, and the account above is complete and useful without them: a test about corruption can already assert on `dropped_corrupted`. **Open for the second half:** a UDP socket cannot send without the checksum through `rustix` 1.1.6 or `nix` 0.31 (neither has `SO_NO_CHECK`), and the workspace forbids `unsafe` (the lint of `Cargo.toml`, D-025). Two ways: one `setsockopt` in a small `unsafe` block of the agent, or a raw IPv4 socket (`SOCK_RAW`, protocol UDP) that sends the UDP header with the checksum field 0, which works with safe code and was tried in a network namespace (the receiver got the datagram). The raw socket is the way that keeps the rule; it needs `CAP_NET_RAW`, which the node has in its user namespace, and it changes what the sender reports for errors. Settled with the maintainer: the raw socket, see D-056 below.

Alternatives: counting the drops from `/proc/net/snmp` (incomplete, D-040: the frames with a damaged destination address have no counter at all); an account per node instead of per direction (a node with two links has two interfaces, and the receive counter belongs to one); an account only for directions that have `corrupt` (the loss that a link without corruption shows is then not accounted for either, and a full buffer would go unnoticed).
