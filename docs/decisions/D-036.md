# D-036: A run counts the packets of each queue with loss and compares them with the packets of the workloads

Accepted. The pattern of lost packets of `netem` is a function of the seed **and of the number of packets that enter the queue**: each packet draws one number. The quiet namespaces (no IPv6, fixed neighbour entries, D-022) keep other packets out, and the patterns were identical on three machines, but a promise of "the same seed, the same lost packets" that the run cannot check would sometimes be false without saying so. ENV-07 was in the ledger for 0.1 and documents described it before it existed; this builds it.

- **What is counted.** After the senders have ended and the run has waited for the packets in the network, the backend reads the root queue of the interface of the sender of each direction that has random loss (`tc -j -s qdisc show`): the packets it sent on, dropped and still holds are the packets that entered it. A direction with a rate and a jitter has a second queue behind the root (D-030); the root draws the loss, so only the root is counted. The root has to be a `netem` queue, else the backend says so.
- **What it is compared with.** The packets that the senders of the workloads put into that direction: `packets` minus the ones the kernel refused (`errors`) in the summary of the agent. Directions without loss are not checked (their queue draws no number that matters), and a run without a seed is not checked (it is not repeatable anyway).
- **What it says.** `seed.queue_checks` lists each direction with `expected` and `counted`; if any differs, `loss_reproducible` is `false`, and the command line names the queue and both numbers. The result format stays at version 0: a field was added, and a reader that does not know it can ignore it.
- **A new method of the backend trait**, `queue_packets`, whose default says "cannot count" (`None`): a backend that cannot count leaves the result as it was. The Kernel backend answers through a new request to the supervisor.
- **How it is tested.** Parsing of the statistics with canaries (the child queue is not counted, no root, a root that is not `netem`, a missing field). In `core` with a fake backend: queues that agree, a packet too many, too few, one in the direction where nothing was sent, no counting, a direction without loss. In real namespaces: the count equals the 417 packets of the workload with one queue and with two, and a canary in which another program sends one more datagram from the node of the sender is found (`counted = expected + 1`).

Alternatives: reading the statistics of the receiving interface as well (it would also count what arrives, which the receivers already record), comparing in the agent (it cannot see the queue), and leaving `loss_reproducible` to the seed and the version of `tc` alone (the state before: a claim without a check).
