# D-053: How the fuzz targets are built and judged (carrying out D-045)

Accepted (2026-11-01). Five targets in `fuzz/` (a crate with a workspace of its own, nightly Rust, `cargo-fuzz` 0.13.2, a fixed dated nightly in the workflow so that a run can be repeated): `scenario` (any text to `Scenario::from_yaml`), `units` (duration, rate, size, probability and name; the first byte chooses), `packet` (`wire::Header::read`), `records` (`records::read`) and `result` (`RunResult::from_json`). The metrics of a program and the replay file get targets with the code that reads them (the supervisor of programs, the replay file).
- **A target is judged by more than "no panic".** What a parser accepts must be valid and must survive a trip through its own output: the scenario is written as JSON (a subset of YAML) and read again and must be equal and still valid; a value prints and reads back as the same value; a header that was read is the one that is written; records that were read are the records that writing them gives; a result that was read can be written and read. The renderer of a refusal is run on every refusal (it cuts source lines at a marked place, where a character boundary can go wrong). The result is not compared field by field: a float can differ in its last digit after text.
- **Seeds.** The scenario target starts from `scenarios/`, `scenarios/invalid/` and `examples/`, so every fault that the corpus knows is a starting point and no copy is kept. The others have a few files in `fuzz/seeds/`: real files from a short run (the record file, the result, with the kernel and the processor replaced) and hand-made edge cases. The corpus that a run grows is not committed; the workflow keeps it in the cache of Actions between runs.
- **The fuzzing is itself tested.** The feature `canary` makes `scenario` panic on an input that starts with `CRASH`. The first job of the workflow, and `just fuzz-canary`, must see that crash, a non-zero exit and the input in `artifacts/`; otherwise a quiet run means nothing. This was run locally (exit status 77, the input kept).
- **Result of the first runs (2026-11-01, this machine):** 15 seconds each for `units`, `packet`, `records` and `result` (3.3 million, 6.9 million, 2.9 million and 0.9 million executions) and 90 seconds for `scenario` (224,000 executions, seeded from all files of the repository): no crash and no failed oracle. That is the start of the corpus, not a statement about the parsers; the weekly run and the longer runs of release 0.8 (ClusterFuzzLite, 24 hours) are what count.
- **A crash becomes a stable test.** The fix comes with the input as a file in `scenarios/invalid/` and a snapshot, or a unit test, so that the CI on stable Rust keeps the case without the nightly. Alternatives: a corpus committed to the repository (it grows without end and says little in a diff); fuzzing in every pull request (minutes of CI for a result that is mostly "nothing"; the weekly run finds the same things a few days later); the unit tests alone (they find what their author thought of).
