# D-066: Ctrl-C stops the workloads and keeps what was recorded

Accepted (2026-11-02). It closes the open point of D-031 and D-022 about the command line: Ctrl-C used to end the program at once, the network was removed all the same (the supervisor sees its pipe close), and the result of the run, which can be long with a timeline, was lost with no message.

- **The first signal stops the workloads and keeps the result.** SIGINT and SIGTERM cancel the run. A new option, `RunOptions::partial_on_cancel` (off by default, so every caller that cancels gets `Error::Cancelled` as before), changes what a cancel does **while the workloads run**: the loop of the run (`drive.rs`) tells every sender to stop with a line `stop` on its standard input, does no more steps of the timeline, waits for the senders to say what they sent, waits the settle time for the packets in the network, collects the records, and returns a result with `timing.interrupted_ns` (when the senders were told to stop). A cancel before the workloads begin or after they ended is still `Error::Cancelled`: there is nothing to keep, or the result is whole (a cancel in the few seconds of the settling loses it; that is accepted for now). The observer gets `RunEvent::Interrupted` (the last variant, D-062).
- **The sender stops in an orderly way.** It reads its standard input also without barriers; a line `stop` ends the stream before its next packet, also while it waits for a barrier (that wait is let go) and while it waits for the moment of the next packet of a slow stream (the waits are sliced in 20 ms). Its summary has `stopped: true` and what it sent. The packets that were never sent are not lost: the sequence numbers end where the sender ended, as for any stream, so the statistics need nothing new. The end of the input does not stop it (a supervisor that died is handled by the supervisor's own pipe, D-022).
- **A signal handler without `unsafe`: `signal-hook`.** The crate is new in `netscenario-cli` only (MIT OR Apache-2.0; `cargo deny` passes; the maintainer agreed). The handler is its, our code stays free of `unsafe` (D-025); a thread waits for the signals and cancels the token. The alternatives from the open point were `ctrlc` (no signal number, so the exit code would be guessed) and a thread on `signalfd` through `rustix` (which does not offer one). The second signal quits at once with the code of the signal; the network is removed all the same.
- **The children must not get the signal of the terminal.** Ctrl-C goes to every process of the foreground process group, and the supervisor, the nodes and the agents were in it. Without a change they died of the same SIGINT at the same moment and the run failed with "the agent ended with killed by signal 2". `KernelBackend` starts the supervisor in a process group of its own (`CommandExt::process_group`, safe), and the nodes and agents inherit that. This is tested with the signal sent to the process group, as a terminal does, and with a canary: without the process group the test fails with exactly that message. It also helps the Python layer: a Ctrl-C in a test reaches Python alone, which cancels through `check_signals` and tears down in order.
- **If the program dies in another way** (SIGKILL, a crash) the pipe of the supervisor closes and it removes the network, as before. A second Ctrl-C relies on that and is tested.
- **The message is written without the lock of standard error.** The first version of the thread wrote with `std::io::stderr().lock()`, and the program holds that lock for the whole `run_command`, so the thread waited until the run was over while the program waited for the thread to end: a deadlock, found by the first test with a real signal. The thread now writes through a copy of the descriptor (`try_clone_to_owned`).
- **Exit code.** 130 for SIGINT and 143 for SIGTERM (128 and the number), with the result written and printed if the workloads had begun, and none (and a line that says so) if not. The code 1 stays for a failed assertion.
- **Python** keeps `Error::Cancelled`: a cancel from `check_signals` raises `KeyboardInterrupt` and gives no result. `Result.interrupted` exists for a result file of an interrupted run.
- **Tested.** The agent: a stop ends a stream of one packet a minute within a second, a stream without a stop goes to its end. The core, with a sender that never ends by itself: the stop line, the order of the events, the result; a cancel without the option or before the workloads is an error. The command line, with real signals to the process group of the program: Ctrl-C gives code 130, the message, a result with `interrupted_ns`, part of the stream with nothing lost, no step of the timeline, and no process left; a second Ctrl-C quits at once and the supervisor removes the network; SIGTERM gives 143.

Alternatives: a partial result in the library for every cancel (a change for every caller, and the Python layer wants the exception); a result written by the signal thread (it cannot know what the run recorded); the settle cut short on an interruption (the packets in flight would count as lost, which they are not).
