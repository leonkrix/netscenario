# D-061: The agent is optimised in the development profile, because it is the instrument (after a CI failure)

Accepted (2026-11-02). The fidelity case of a stream without the checksum at 1,200 bytes (4,000 packets a second, 38.4 mbit) ran past the watchdog of 30 seconds on the Ubuntu 22.04 runner, once. The same case had passed in three pull requests before. The cause is not the case but the build: the tests start the agent from `target/debug`, and an unoptimised agent is slow enough to matter.

- **Measured on the development machine, a quiet one.** The receiver of that stream took 49 % of a core in the debug build (the receive loop, the CRC-32 of every packet, the tap that reads the frames) and 2.7 % optimised; the sender takes 85 % in both, because it spins for the last stretch before each packet by design (`docs/AGENT.md`). With 24 busy loops on 4 cores the debug build did not finish: the senders were still sending after 37 seconds ("the agents did not end in time"), and a run that did finish had 14.2 % loss against the 9.9 % the case expects, the difference being datagrams that the starved receiver let the socket buffer drop. The optimised agent under the same load finished in 7.2 seconds (5 s of traffic, 1 s of settling) and passed the case twice in a row, as it does on a quiet machine.
- **The change.** `[profile.dev.package.netscenario-agent]` and `[profile.dev.package.rustix]` have `opt-level = 3` in the workspace manifest. `rustix` makes the system calls of the agent. Debug assertions and overflow checks stay on, the tests of the agent crate are as before, and nothing else changes: the supervisor and the core are not on the hot path.
- **Why this and not more time.** Raising the 30 seconds of the tests would have hidden a measurement that was wrong for a reason (a receiver that lost packets because it was slow, not because the network did), and the case would then have failed on its bounds. Lowering the rate of the case would have changed what it measures. An instrument that is fast enough on a loaded machine is the fix that keeps the cases as they are. The fidelity page says that a busy host changes the numbers; this is what makes the cases tolerant to it.
- **Not done:** a limit on how much the agent may take, and a check in the result that the receiver was not starved (`receive_buffer_drops` in `directions` already says it did lose datagrams to a full buffer, and the unaccounted-packets bound of the cases fails on it).
