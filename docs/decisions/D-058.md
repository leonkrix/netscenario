# D-058: The pattern of the arrivals is computed in the core from the first arrivals, by the definitions of the RFCs

Accepted (2026-11-01), for PRB-04 and PRB-06. The statistics are in `patterns.rs` of the core and do not depend on the backend: they read the records that every backend produces.

- **What is computed.** The extent and the late time of the reordered packets (RFC 4737, sections 4.2 and 4.3), the interarrival jitter (RFC 3550, appendix A.8), and the runs of lost packets (the "loss period" of RFC 3357). Each is a field of the statistics of a workload and is absent or empty where there is nothing to say.
- **Which arrivals.** The first arrival of each packet, in the order it happened (`first_arrivals`): RFC 4737 section 3.6 analyses only the first copy, and the delays of the result are the same. A number the sender never used is not an arrival. The loss runs use the same set, so a packet that arrived damaged (`corrupted`) is in a run, as it is in `lost`.
- **The extent.** As the RFC defines it: for the reordered packet at arrival position `i`, `i - j` for the smallest `j` with a higher sequence number. The earliest arrival with a higher number is always an arrival that raised the highest number so far (everything before it was lower than the packet), so it is found by a binary search among those, in ascending order, and the run costs `O(n log n)` where the definition costs `O(n^2)`. Late time (`DstTime(i) - DstTime(j)`) comes with the same scan for nothing, and it is the number that sizes a jitter buffer, so it is included. Not computed: the byte offset and the gap of RFC 4737 (the export of every packet has what they need).
- **The jitter.** `J = J + (|D| - J) / 16` over `D = (R_j - R_i) - (S_j - S_i)` with the pairs **in the order of arrival**, as the RFC says (the packets of a pair need not be neighbours in sequence). Both times are readings of the one clock of the machine, so `D` is exact and needs no estimate of an offset. The RFC defines a running estimate and not a number for a run; the result has the estimate after the last packet (`last_ns`), its mean over the run (`mean_ns`) and its largest value (`max_ns`). The mean is what a test should assert on, because the last value depends on the last sixteen packets alone. These three summaries are this project's, not the RFC's, and the documents say so.
- **The loss runs.** Runs, longest, mean (`lost / runs`) and a histogram by length, as a list of `{length, runs}`. The first version had a map from length to count; it could be written but not read back, because `WorkloadResult` flattens the statistics and the flattening cannot read an integer key from the text of a key.
- **How it was tested.** The code is compared with every worked example of RFC 4737, section 7 (the extents of 7.1 to 7.4, the late times of 7.1 and 7.3), with the slow definition on all 720 orders of six packets and on a long series, with the closed form of the estimate for a series of known transit times (`10 ms x (1 - (15/16)^n)`, and 0.625 and 1.2109375 ms by hand for the first steps), with a stream of constant transit time (no jitter whatever the spacing) and with a pair of packets that swap (the pairs of the order of arrival). A burst and a scattered loss of the same size must differ in the runs. And against the real network: a uniform jitter of 10 ms with a packet every millisecond. An independent simulation, written apart from the code under test and run 120 times with 6,000 packets, gives a jitter of 3.543 ms (standard deviation 0.032 between runs), a mean extent of 3.70 and a mean late time of 3.185 ms; the first run of the case measured 3.500 ms, 3.65 and 3.194 ms. The jitter is not the 10 / 3 = 3.33 ms that two neighbours in sequence would give: the pair of an arrival and the one before it depends on the delays that put them there. The fidelity test also counts the runs its own way and fails if the result disagrees.
- **Python.** The jitter of a measurement is `InterarrivalJitter` there, because `Jitter` is the impairment that the scenario builder already exports.

Alternatives: computing the jitter from pairs in sequence (not what the RFC says, and for a link with a jitter it gives 3.33 ms where the RFC gives 3.54); only the count of reordered packets (it does not say whether a buffer of 3 packets would do or one of 300 is needed); leaving the statistics to the test code (a result should carry what a person looks for first).
