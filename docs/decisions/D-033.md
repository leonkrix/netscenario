# D-033: One platform wheel carries the extension module, the supervisor and the agent, and the command

Accepted. How the wheels are made is in [PYTHON.md](../PYTHON.md), "Installing".

- **One wheel per architecture, the stable ABI.** `cp311-abi3`, so one wheel serves every Python from 3.11 on (D-017); it is a platform wheel because of the programs in it. manylinux_2_28 (glibc 2.28: Debian 10, Ubuntu 20.04, RHEL 8 and everything newer) is the oldest platform that the target audience of CI runners and developer machines does not leave behind.
- **The programs are in the wheel, not downloaded and not built at install time.** A run needs the supervisor (the program is its own supervisor, D-022) and the agent, and Python cannot stand in for either (D-031). The wheel has them in `netscenario/_bin`, built in the same manylinux container as the extension module, so they link only to the C library of the old distribution. The files keep their execute permission (checked in the wheel). The alternative, a second package for the programs, would give a Python package that fails at its first run when the two versions do not match.
- **The command `netscenario` is a launcher.** `pip install` gives the command through an entry point that replaces the Python process with the bundled program (`os.execv`), so signals, exit codes and the terminal are the program's. `python -m netscenario` does the same. No Python stays in between.
- **The lookup is in the order of trust**: the environment variable, then the package, then a checkout of the repository. A wheel that lacks its programs does not borrow them from a checkout by accident (the smoke test installs into a clean environment and removing the programs makes it fail, which was tried).
- **Built on a runner of each architecture, natively.** The Arm wheel is built on a GitHub-hosted Arm runner in the aarch64 manylinux container, not cross-compiled or emulated: no emulation to be slow or wrong, and the install test then runs on the same architecture. The action that does this, `PyO3/maturin-action`, is pinned to a commit, as is the version of maturin (the action checks its checksum).
- **A wheel is tested where it is installed.** The job `wheel-test` takes the wheel from the build, makes a clean environment with `uv`, installs the wheel and the plugin, and runs `python/smoke/wheel_smoke.py` from outside the checkout with `python -I`: the package must come from `site-packages`, the programs from inside it, the command from the `bin` directory of the environment, `doctor` must say ok, a scenario must run through the installed package, and an inner `pytest` must run one through the installed plugin. It runs on Ubuntu 22.04 with Python 3.11, on 24.04 with 3.14, and on Arm with 3.12. The same script runs locally with `just wheel-smoke`.
- **Not in this step.** The upload to PyPI, signing and provenance of the wheels (REL-01 to REL-03), musllinux wheels, and a static agent. The wheel is tagged `linux` when built locally and manylinux when built by the CI.

Alternatives: `cibuildwheel` (a general tool for Python extensions, more than is needed for one module and two programs and it tests with pytest inside the container, which cannot create namespaces), cross-compiling or QEMU for Arm (slow and a source of errors that a native runner does not have), a source distribution only (every user would need Rust and the build of the programs), and a `data` directory of scripts instead of `_bin` (installs the programs outside the package, where the package cannot be sure to find its own).
