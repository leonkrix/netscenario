# D-065: Two workloads in a direction whose queue draws random numbers are not a repeatable experiment, and the result says so

Accepted (2026-11-02). It carries out the last open part of D-038. The lost packets of a seed are a function of the seed **and of the order in which the packets reach the queue**: the n-th packet that enters draws the n-th number. With one workload in a direction that order is its schedule. With two, their packets are microseconds apart and which one comes first changes from run to run on a real kernel (D-038), so the same seed loses the same number of packets and not the same packets. Release 0.1 said `loss_reproducible: true` there; release 0.2 with a timeline said `false` only if a step changed what is drawn (D-062). Now it is said for the whole run.

- **The rule.** A direction that two or more `udp-cbr` workloads send into, and whose queue draws numbers that the seed is to repeat (a loss, a duplication, a corruption or a reordering, in the impairments at the start or in any state that a step leads to), makes `seed.loss_reproducible` `false`, with one sentence that names the workloads, the link and the direction. A direction that nothing is drawn for (a delay, a rate) says nothing, one workload each way says nothing, and an outage is not a draw (D-064).
- **Not the queue check.** The count of the queue (D-036) agrees here, because it sums the packets of both workloads. It tells whether something else entered the queue, not in which order; so the reason is made from the scenario and not from the count. A program of your own that sends into the direction is still told by the count.
- **A change of an existing result, on purpose.** A scenario of release 0.1 with two workloads in one lossy direction had `true` and has `false` now, with the warning on the command line and in the report of a test. That is the correct statement and it is visible; the numbers and the files of the result do not change.
- **The step reason of D-062 for two workloads is gone**, because this one covers it for every case and the two would have said the same thing twice.
- **Tested.** With the fake backend: two in one direction name both and are not reproducible; canaries: one each way, one alone, two without a draw, and a duplication that only a later step brings. In real namespaces: two workloads in a lossy direction give the reason, and the queue still counts the packets of both.

Alternatives: leaving it to the count of the queue (it cannot see the order); a refusal of such a scenario (a test of two streams through one link is a good thing to run, only not an exactly repeatable one); a `true` with a warning in the notes (the field would lie).
