# D-059: A direction keeps its queues for the whole run, and a change writes the whole state into them

Accepted (2026-11-01). It is the foundation of the timeline on the Kernel backend (D-038, D-048, D-050) and changes nothing for a scenario without one. Nothing applies the timeline in a run yet (D-060), so `Scheduled steps` is still declared as planned.

- **The layout is made from every state, and it does not change.** A direction is one `netem` or two (the rate in the first, the delay with its jitter and the reordering in the second, D-030). Which one it is depends on the state: a rate together with a jitter or a reordering needs two. A timeline can lead a direction from a state of one kind to a state of the other. *The cheaper route* is to build the queues again when the kind changes. It was not taken for two reasons that follow from D-038: a queue that is built again drops the packets that are in flight (their number depends on the delays, not on the packet numbers, so the lost packets of two runs with one seed would differ), and it starts its generator again (the seed that the run promises to repeat). So the core tells the backend all the states of a direction before it is built (`Backend::plan_states`, with a default that does nothing; `timeline::states_of`), and the backend builds the layout that every state fits: two queues for the whole run if any state needs them, also while the rate is not set (a queue without a rate and a delay passes packets on at once), the longest limit of any state so that a change never makes it smaller than the packets it holds, and a seed for each queue that draws numbers in some state, because a change keeps the generator and cannot give a queue a seed it was built without. A direction that is not changed, or whose states fit one queue, is built as before: every argument of the unit tests of release 0.1 and 0.2 is the same.
- **A change writes the whole state** (`Backend::change`, `netem::change`). Measured on kernel 6.12 with iproute2 6.15 (the matrix is the test): after a `change` that does not mention it, `corrupt`, `reorder` (and its gap), `rate` and `slot` are still in force, and `delay`, the jitter, `loss` of any model and `duplicate` are gone. So a change writes `corrupt 0%`, `reorder 0%` and `rate 0bit` where the state has none, and nothing else; it carries no seed. A test goes from every state to every state (11 states for one queue, 12 for two, 121 and 144 pairs) and compares the queues with a fresh set built for the target (kind, place in the tree, every option but the seed); a canary does the change by hand without the zeros and must differ.
- **A new finding: the distribution of the jitter cannot go back.** The options of a queue do not show the table of the distribution, so it was measured by the round trip time of 300 pings (a delay of 20 ms with a jitter of 5 ms): normal, 5.04 ms of deviation; after a `change` to the same without `distribution normal`, 5.03 ms; a fresh uniform queue, 3.04 ms (5 / sqrt(3) = 2.9 expected). `netem` keeps the table that was loaded last, and `tc` has no word for uniform. The only way back is to build the queue again, which is what the layout rules out. So the backend **refuses** a timeline in which the jitter of a direction is normal in one state and uniform in another, with the step that leads to the second distribution named (`timeline_refusals` in `check_values`), the way out being one distribution through the run (the amount may change, the jitter may go away and come back) or the Engine backend. Not taken: building the queue again with a note in the result (it would be an approximation that the project does not make silently, and the packets it drops are the ones the test is about), and letting the table stay (a test that asks for a uniform jitter would measure a normal one).
- **The requirements follow the states.** `requirements` asks for the features of every state a `set` leads to, with the path of the step (`timeline[0].set.reorder`), so a backend that cannot reorder refuses a scenario whose reordering starts at 5 s. The seed is needed (`SeededLoss`) if some state draws numbers; an outage draws none that the seed is to repeat (D-064), and a scenario with an outage alone needs no seed.
- **Where it lives.** `netscenario_core::timeline` (`steps`, `states_of`, `draws_random_numbers`) turns the file into what a backend does: at a moment, this direction has these impairments from now on (the whole state), or an outage begins or ends in it (D-064; first written as a loss of 100 % in the state, which it no longer is; the constant `Probability::ALWAYS` that was made for it stays in the model), or the interface goes down or up.
- **Not in this step, on purpose.** A change starts one `tc` process through `nsenter` (about 1 ms, 3.6 ms with a busy machine, S11); D-038 asks for a `tc -batch` that lives for the run (0.03 ms) with a time limit and a fall back after the hang that S11 saw on a runner. That is performance of the barrier and comes with the barrier (D-062 made it a step of its own, and D-063 did it). The run, the result `events`, the observer and the cancel token are D-060; `down`, `up` and `outage` as events came with D-064.

Alternatives: one `netem` always (the 0.1 design; it cuts the jitter off below with a rate, D-030); two queues always (one more hop for every packet, and another draw order, for no gain where the direction needs one); rebuilding on a change of kind (above).
