# D-075: A run records its scenario, and a replay runs it with the recorded seed and compares the lost packets and the machine

Accepted (2026-11-03). Closes ENV-03. D-043 decided that a result directory gets `scenario.json` and that `netscenario replay <dir>` runs it again; this decision settles how.

- **`scenario.json` is the scenario exactly as it ran**: the canonical JSON (the keys in the order of the format, defaults left out), indented. Its fingerprint is the one in `result.json` (`scenario.hash` is the SHA-256 of the same canonical JSON, compact), so a reader checks that the two files belong together whatever the layout of the file. The seed that a run drew is in the result and not in the scenario, so **the replay sets the recorded seed**; a seed given with `--seed` or by the file is in the scenario already and the recorded value is the same. The file is written just before `result.json`: a directory with a result always has it. A directory written by an older version has none, and the replay says so instead of guessing.
- **The replay refuses a directory it cannot trust**: a directory without a result, the directory of a set (it names `run-001` as the thing to replay), a scenario that is not valid, and a `scenario.json` whose fingerprint is not the result's (both are named). Nothing is run then (exit code 2).
- **The replay waits as long as the original** (`timing.settle_ns`), not for the default wait: what counts as lost depends on how long the run waited, and the default is derived from the queues of the run. A replay that waited another time could lose other packets for that reason alone.
- **What is compared is the loss and the machine, not the delays.** For each workload the sequence numbers that never arrived intact, read from the records of the two runs; delays and rates vary from run to run on one machine and are not compared. The provenance is compared field by field (the backend and its details such as the version of `tc`, the kernel, the processor, the version of netscenario; not the time): a difference in the first four is "another machine", because the lost packets of a seed are a function of the kernel's `netem` and of `tc`.
- **The verdict has four values.** `reproduced`: the same packets. `differs`: other packets although both runs said that the loss repeats from the seed (`loss_reproducible`): the replay failed, **exit code 1** (the code of "a check was asked and did not hold"), and the summary names the packets and, where the machine differs, offers that as the likely reason. `not-promised`: other packets, but one of the runs said that its loss does not repeat (an outage, corruption, a program that sends, a queue that counted a packet nobody sent): no failure, exit 0, with the reasons. `not-comparable`: the original was interrupted, or the records cannot be read.
- **`--scenario <file>` answers "has my file changed since that run?"** It compares the file with the recorded scenario field by field (path, the value in the run, the value in the file) and replays nothing if they differ; the replay always runs the recorded scenario and never the file (D-043 rejected a replay from the name of a file). A file without a seed does not differ from a run that drew its seed. The keys of `measure` that an option of the run replaced are differences, as they are: the run measured something the file does not say.
- **The programs of your own run in the directory where `replay` is run**: the directory of the original is not recorded (a result may be shared, D-027), and the summary of the original's programs says what ran. This is the one thing a replay cannot promise.
- **Tested:** the loading and every refusal; the fingerprint independent of the layout; the field diff (a changed field, an added workload, the drawn seed); the comparison of lost packets (same, other with the same counts, the list cut with exact counts, not promised, not comparable) and of the machines; the summary text; in real namespaces the replay of a lossy run (the same packets), the refusal of a changed `scenario.json` and of a different file, and, as the canary of the comparison, a replay with another recorded seed that must fail with exit code 1.

Alternatives: replay from the scenario file (the file may have changed, D-043); the default wait for the replay (above); comparing delays with a tolerance (they vary, and a tolerance would be a bound by eye); exit 0 for every replay and the verdict only in the text (a script cannot tell, and a replay that does not reproduce is the one thing it is run to find out).
