# D-057: The damaged packets of a corrupting direction are named by a tap in the receiving agent

Accepted (2026-11-01), on the ground of D-040, D-047 and the spike S13b. It carries out the part of D-040 that names the corrupted packets by sequence number, and it writes the frame reader that the capture of packets (D-047) will use.

- **What is built.** A receiver started with `--wire-out <file>` opens a packet socket (`AF_PACKET`, all protocols) in its node and writes a record, in the format of the record file, for every frame that is a packet of its stream, whether or not the stack then delivers it. The run subtracts the sequences in the receiver's own records and keeps those that are below `sent`: these are the packets that arrived damaged (`name_damaged` in `stats.rs`). The core asks for the tap only for a workload whose direction has `corrupt`, so a scenario without corruption opens no packet socket. The tap uses `rustix` (no `unsafe`, no new dependency): it needs neither the binding to an interface nor the kernel timestamps that D-047 takes `nix` for, and it does not bind, because the destination address and port select the stream. The capture of packets adds those two and the pcap writer on top of the same `packet_in_frame`.
- **What counts as a named packet, and why that is stricter than the spike.** A frame is named only if the type of Ethernet, the version and header length of IP, its protocol and destination address, the destination port of UDP, and the magic, version, flags and sequence number of the agent are intact (18 bytes). The spike S13b read frames more loosely (it did not look at the destination) and named 94, 97 and 99.3 % of the corrupted packets at 64, 200 and 1,200 bytes. *The cheaper route* was to accept a frame as a packet of the stream by its magic alone; it would name about 11 points more at 64 bytes and has a flaw that the spike could not show, because it had one stream and one interface: a frame whose destination port is damaged may belong to another stream of the node, and giving its sequence number to this one is a wrong name. A wrong name is worse than none, so the filter is strict, and the figures are lower: **82, 92 and 99 %** of the frames the node dropped (the model in the fidelity cases: `(frame - 6 - 18) / (frame - 6)`, and the measured 83.0, 92.9 and 99.0 % in the first run on the development machine and 81.9, 92.6 and 98.4 % in the second, scattered around the model and each within four standard deviations). Not taken: guessing the stream from the sequence numbers that fit.
- **It is a help and not a condition.** The packet socket needs `CAP_NET_RAW` in the node, which a process with only the two ambient capabilities of PERMISSIONS.md lacks. Before this step such a process could run a scenario with `corrupt`, and it still can: the receiver says in its `ready` line why the tap is not there (`wire_error`), the run goes on, the damaged packets are counted exactly for the node (`directions`) and the workload says `corrupted_seq_unavailable` with the reason. `doctor` shows the same capability as `raw-socket`. A run does not refuse a scenario for it.
- **What the result says.** `corrupted_named` (the count), `corrupted_seq` (the first 1,000 numbers, ascending) and `corrupted_seq_unavailable` on the workload; the export of every packet (`--packets`) marks all of them with `corrupted`. The list is cut because 10 % of a long run at 100,000 packets per second is hundreds of thousands of numbers, and the file with every packet is the place for all. Not taken: the list uncut in `result.json`; a count of the unnamed ones in the tally of the direction (a stream without the checksum names damaged packets that the node delivered, so the difference to `dropped_corrupted` would not be the number it says).
- **What it does not claim, and when the names are withdrawn.** A bit flipped in the sequence number gives another number, which is named if it is in range and was not delivered. On a link that only corrupts, that number is a packet that was damaged too, so the set is right although the frame is attributed to a neighbour; with a loss in the direction it can be a packet that the queue dropped. The documents say so. And a datagram that the node dropped because a receive buffer was full is also seen on the wire and not delivered, though it is whole: where the tally counts `receive_buffer_drops` the names are withdrawn, with the reason, because they would be wrong. The test that has no loss checks the one thing that can be checked from outside: there are never more names than frames the node dropped.
- **The wire is read by the receiver, not the sender.** What the sender sent is in its records; what the node dropped is seen only at the receiving interface, after the queue (D-047: the tap sits after the queue, and a packet that the queue dropped is in no capture). So a packet the queue dropped is not named, because its frame was never there to be seen (the one way round it is a bit flipped in the sequence number of another frame, above), which is the difference between the two that D-040 asks for.

Alternatives: reading the sockets error queue (a datagram with a bad checksum is dropped before any socket sees it); counting from `/proc/net/snmp` (D-040: incomplete); a tap in the supervisor of the run (the supervisor is outside the node, and a packet socket there would see the host).
