# D-050: The timeline in the format

Accepted (2026-11-01, the first part: the timeline; `kind: command` follows in its own pull request). The format reads `timeline` now; the Kernel backend applies it later in release 0.2 (done: D-059 to D-064) and refuses it until then (a `Feature` each for `set` (`Scheduled steps`), `outage` (`Outages`) and `down`/`up` (`Link down and up`), declared `Unsupported`; the rows of the coverage page say `✔ 0.2`).
- **An event does exactly one thing**: `set`, `outage`, `down` or `up`, in an event with `at` and `link`. The sketch of Part 2 had `down` and `up` as actions without a value; `down: true` keeps the word and gives the key a value, and `down: false` is refused because it would say nothing.
- **`set` has the shape of the impairments, not dotted keys.** The sketch wrote `set: { forward.rate: 2mbit }`. The nested form `set: { forward: { rate: 2mbit } }` reuses the names and the types of the impairments of a direction (so the schema, the units and the hints are the same), and `both` works as it does in a link. It is a JSON merge patch (RFC 7386): a key not written stays, a value replaces the old one as a whole, `null` takes the impairment away. Without `null` there would be no way back to a link without a rate; with a `clear` list there would be a second way to say it.
- **Every step is checked as a state.** The reader walks the events in time order (a stable order, events at one moment in the order of the file), applies each `set` to the impairments of the direction and runs the rules of a direction on the result (a jitter needs a delay, a reorder needs a delay, the jitter does not reach below zero). A problem that the link has from the start is reported with the link, and one that a step causes is reported once, with "after this step". The backend then never meets a state that the file did not show valid.
- **An outage is a window, and windows do not overlap.** An outage of a direction while another one is going on in a direction they share (`both` overlaps both) is refused: the end of the first would be unclear. A `loss` that is set inside an outage was refused too (the outage was a loss of 100 %, and "which value wins" is a question that a file should not leave to the scheduler); **D-064 took this rule away**: an outage is not a value any more, it is a window that acts after the queues, so there is nothing to win. The alternatives were a rule (the outage wins, the set takes effect at its end) that a reader of the file would have to know, and no check at all. The checks can be relaxed later without breaking a file; a rule cannot be added to files that exist.
- **An outage ends inside the measured phase** and is longer than zero; an event is before the end. A link goes down only if it is up, and comes up only if it is down: a second `down` is a typo more often than an intention.
- **`direction` belongs to `outage` only.** The interface of a link has both directions (a `veth` pair loses its carrier on both ends), and `set` names its directions already.
- **Released with the types:** `Event`, `Change`, `ImpairmentsChange`, `Direction`, `True` in `netscenario-model`, `Scenario::timeline`, and the constructors `Event::set`, `outage`, `down`, `up` with `ScenarioBuilder::event`. `Scenario` gets a field, so the API breaks (`feat!`); a scenario without a timeline writes none, so the hash of every existing scenario stays.
