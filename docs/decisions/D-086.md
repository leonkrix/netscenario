# D-086: TCP and request/response are measured by their bytes and times, the kernel's TCP is the subject, and the result says whether a run can be repeated exactly

Accepted (2026-11-05). For WRK-04, WRK-05 and PRB-12. S18 measured what TCP does in the namespaces; these are the decisions made before building it.

- **The kernel TCP of the host is the subject.** The workloads use the TCP stack of the machine, so its version goes into the provenance, with the congestion controls the host offers.
- **What is recorded.** For bulk transfers: bytes and goodput by time bin, the completion time of a transfer, the retransmissions and `TCP_INFO` samples (round trip time, congestion window, retransmits) at a fixed interval. For request/response: one record per request (start, end, bytes). Per-packet analysis of TCP is done through the capture, not by the agent.
- **Congestion control is chosen per workload** with `cc: cubic | reno | bbr`. **Without it `cubic` applies, whatever the host's default is**, and the result names the one used, so that the same file means the same on two machines. A host that lacks the module (`bbr` on the runner images) refuses the scenario before anything is built, with a message that names the feature and the host.
- **Offloads are off on every veth, in every run, and it is done with `ip`, not `ethtool`.** With them on, `netem` counts a super-packet of up to 44 segments as one packet and TCP ran 40 to 60 % over the model of Mathis; off, the ratio was 0.88 to 1.13 (S18). It is done for UDP runs too, so that one network behaves in one way whatever runs in it. It costs throughput only at rates far above what a test needs. `ethtool` is not on every machine (not on the maintainer's, and the project installs nothing system-wide), and the stack builds its segments from the largest size and the number of segments the device accepts, which `ip link set <if> gso_max_size <mtu + 14> gso_max_segs 1` sets in the node, at both ends of every link, and again when the MTU of a link is set. Measured on 2026-11-05 on Debian 13 (kernel 6.12, reno, 40 ms round trip, loss on the data direction, 25 s, against `MSS/RTT x 1.22/sqrt(p)`): with the defaults 1.79, 1.42 and 1.36 times the model at 0.5, 1 and 2 % loss; with the limit 1.16, 0.97 and 1.08. The doctor probes that `ip` accepts it (`segments`). The receiving side's GRO is not touched: it merges after `netem`, and a router forwards what it received segment by segment (to be confirmed by the fairness experiment over a dumbbell).
- **A class of reproducibility in the result:** `exact` for what is seeded and packet-synchronous (UDP), `statistical` for anything that is driven by feedback (TCP), with the reason. A statistical run is repeated and read with the interval (repetitions of 0.2), not compared bit for bit.
- **The round trip (PRB-12) is in this step for both kinds:** the time of a request to its response with percentiles, and the round trip of a datagram stream with an echo, from the same records.
- **The recovery after an event** works on bytes for these workloads, not on packets.
- **Three pull requests:** the agent with its wire format, the core with the result and the command line, the format with the builder and the docs. The programs of your own keep working next to them.

Alternatives: the host's default congestion control (the same file means different things on two machines); offloads off only for TCP (two behaviours in one network); per-packet records of TCP in the agent (the capture has them, and the agent would have to read the stack's mind); UDP echo as a step of its own (the echo path is small and the result would have two ways to say the round trip).
