# D-086: TCP and request/response are measured by their bytes and times, the kernel's TCP is the subject, and the result says whether a run can be repeated exactly

Accepted (2026-11-05). For WRK-04, WRK-05 and PRB-12. S18 measured what TCP does in the namespaces; these are the decisions made before building it.

- **The kernel TCP of the host is the subject.** The workloads use the TCP stack of the machine, so its version goes into the provenance, with the congestion controls the host offers.
- **What is recorded.** For bulk transfers: bytes and goodput by time bin, the completion time of a transfer, the retransmissions and `TCP_INFO` samples (round trip time, congestion window, retransmits) at a fixed interval. For request/response: one record per request (start, end, bytes). Per-packet analysis of TCP is done through the capture, not by the agent.
- **Congestion control is chosen per workload** with `cc: cubic | reno | bbr`. **Without it `cubic` applies, whatever the host's default is**, and the result names the one used, so that the same file means the same on two machines. A host that lacks the module (`bbr` on the runner images) refuses the scenario before anything is built, with a message that names the feature and the host.
- **Offloads are off on every veth, in every run, and it is done with `ip`, not `ethtool`.** With them on, `netem` counts a super-packet of up to 44 segments as one packet and TCP ran 40 to 60 % over the model of Mathis; off, the ratio was 0.88 to 1.13 (S18). It is done for UDP runs too, so that one network behaves in one way whatever runs in it. It costs throughput only at rates far above what a test needs. `ethtool` is not on every machine (not on the maintainer's, and the project installs nothing system-wide), and the stack builds its segments from the largest size and the number of segments the device accepts, which `ip link set <if> gso_max_size <mtu + 14> gso_max_segs 1` sets in the node, at both ends of every link, and again when the MTU of a link is set. Measured on 2026-11-05 on Debian 13 (kernel 6.12, reno, 40 ms round trip, loss on the data direction, 25 s, against `MSS/RTT x 1.22/sqrt(p)`): with the defaults 1.79, 1.42 and 1.36 times the model at 0.5, 1 and 2 % loss; with the limit 1.16, 0.97 and 1.08. The doctor probes that `ip` accepts it (`segments`).

  **`ethtool` was measured next to it (2026-11-05, three runs each, reno, 40 ms round trip, 15 s, ratio to Mathis; direct = loss on the sender's own interface, router = loss on the egress of a router):** direct, none 1.2 to 6.4, `ethtool` (`gso off tso off gro off`, both ends) 1.2 to 4.5 and three more runs alone at 2.7 to 3.5, `ip` 0.88 to 1.28 (mean 0.92 to 1.16); through a router, none 1.2 to 3.3, `ethtool` 0.87 to 1.46 (mean 1.03 to 1.24), `ip` 0.92 to 1.33 (mean 1.05 to 1.21). So `ethtool` is not just another tool for the same job: it does not work where the loss sits on the sender's own interface, which is where the backend puts it. The reason is in the kernel: a TCP socket always has `NETIF_F_GSO` in its route capabilities, whatever the device says, so the stack builds super-packets and the software segmentation happens after the queue, when `netem` has already dropped or delayed the whole super-packet; through a router the segments have been cut at the first hop. Capping the size where the packet is made works in both. GRO is off by default on a veth (kernel 6.12, `ethtool -k`), so there is nothing to switch off on the receiving side. Not measured: a path through the fabric of D-079 (the cap sits on the interfaces of the nodes, where the segments are made, so it should not matter) and other kernels; the fairness experiment over a dumbbell is the next place it shows.
- **A class of reproducibility in the result:** `exact` for what is seeded and packet-synchronous (UDP), `statistical` for anything that is driven by feedback (TCP), with the reason. A statistical run is repeated and read with the interval (repetitions of 0.2), not compared bit for bit.
- **The round trip (PRB-12):** the time of a request to its response with percentiles, from the records of the requests (done in the third pull request). The round trip of a datagram stream with an echo was meant to be in the same step: the agent has it (`recv --echo-to`, the first pull request), but a workload kind or a key that uses it needs a key on five UDP kinds, a collecting receiver in the sender's node and a field in the result, so it follows in a pull request of its own (done, D-087).
- **The recovery after an event** works on bytes for these workloads, not on packets.
- **Three pull requests:** the agent with its wire format, the format (the two kinds, their checks, the builders and the docs: the core cannot run or test a kind that the model does not have, so the format comes before the run), and the core with the result and the command line. Until the third, the Kernel backend refuses a scenario with these kinds and names the feature. The programs of your own keep working next to them.

Alternatives: the host's default congestion control (the same file means different things on two machines); offloads off only for TCP (two behaviours in one network); per-packet records of TCP in the agent (the capture has them, and the agent would have to read the stack's mind); UDP echo as a step of its own (the echo path is small and the result would have two ways to say the round trip).

**What the third pull request built (2026-11-05).** The core starts a server in `to` after the receivers and the programs, and the clients at the beginning of the measured phase with the `start` of each, waits for the clients to be done (they end by themselves; an interrupted run tells them to stop), and then stops the servers (`tcp.rs` of the core). The result has a `tcp` entry for each workload and a top-level `reproducibility` (`exact` or `statistical`, with the reasons). The Kernel backend refuses a congestion control that the machine does not offer, by name and with the line of the workload, before anything is built, and puts the controls it offers in `provenance.backend_details`. A run with a TCP workload is not accounted for packet by packet (`directions`, and the check of the queues against the packets sent, are left out), because the acknowledgements and the retransmissions enter the same queues; the counters of the queues are still read. The recovery after an event for bytes is not built: it needs a definition of the level of a bin that is not packets sent and delivered, which is a decision of its own.
