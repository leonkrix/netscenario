# D-097: The precision of the timers is measured by the process that starts a run, recorded in its provenance, and reported in full by `doctor --timers`

Accepted (2026-11-10), for ENV-05. How late a sleeping core wakes depends on the processor, its idle states, the timer slack of the process and the load (D-015), so the engine reports what the machine does and never promises a figure. This decides what is measured, where, and what is judged.

- **What is measured** (`netscenario_core::timers`, `std` only). The clock: the source of `CLOCK_MONOTONIC` (`/sys/devices/system/clocksource/clocksource0/current_clocksource`), what a reading costs (the median of 4,000), and the smallest step seen between two different readings. Sleeps: how much longer than asked `std::thread::sleep` took, for 200 microseconds (the stretch between two packets of a fast stream) and 1 millisecond, as the number of samples, the median, the 99th percentile (nearest rank) and the largest. It is the call the senders and the steps of a timeline wait with, so the number is the lateness they meet. Around it: the timer slack of the process, the governor of the first processor, and the load average with the runnable tasks, read before the measurement adds its own.
- **Recorded in every run** (`provenance.timers`, optional, absent in older results). The run measures about 40 milliseconds (50 sleeps of 200 microseconds and 20 of 1 millisecond) just before it builds the network, so that it does not meet its own probe. So few samples make the 99th percentile close to the largest; each entry says how many there were. The lateness a run actually met stays where it was: `max_lateness_ns` of each sender and `applied_ns - scheduled_ns` of each step in `events`. The probe is the machine before the run, those are the run.
- **Reported in full by `doctor --timers`** (about two seconds: 1,000 sleeps of 200 microseconds and 300 of 1 millisecond). It adds what only the Kernel backend can say: what a change of a qdisc costs through the `tc` that lives for a run (D-038), 500 changes of a `netem` in a network namespace of its own (a `pfifo` where the kernel has no `netem`), which is what a step of a timeline waits for. `doctor` without the flag stays as fast as it was and prints no timers.
- **A warning, never a failure.** The checks are `ok`, `info` or `warn`, so the exit code of `doctor` does not change. A sleep whose 99th percentile is later than 150 microseconds warns, because a sender sleeps until 150 microseconds before the slot of a packet and spins for the rest (`sender.rs`): a later wake-up sends the packet late. A clock reading above one microsecond warns (a `hpet` or `acpi_pm` source, a virtual machine that traps it). A load average above the number of processors warns. A change of a qdisc whose 99th percentile is above two milliseconds warns (D-063 measured 0.03 to 2 ms). A run is never refused because of a timer: the result says what the machine did.
- **Python.** `Result.provenance.timers` and `ns.doctor(timers=True)` (`DoctorReport.timers`, `tc_change`), in seconds like the rest of the Python layer.
- **The text and the page of a run** have one line, `Timers`, when the result has the numbers.

Alternatives: measuring in the agent in a node (a probe for each node and each run, and the agent is the process that sleeps, but a namespace changes nothing about how a core wakes, and the result would hold one record for each agent); measuring at the end of the run (the machine after the load of the run, not the one it ran on); a probe only on request (a result could not say what machine it was made on, which D-015 asks for); a verdict that refuses a run on a machine with late timers (a run on a loaded machine is a valid, if less exact, measurement, and the result shows how much less); recording the `tc` change cost in every run (a namespace for the probe, for a number the steps of the run give anyway).
