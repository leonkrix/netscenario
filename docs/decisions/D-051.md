# D-051: `kind: command` in the format

Accepted (2026-11-01, second part), on the ground of D-041. The format reads a workload of kind `command` now; the Kernel backend starts programs later in release 0.2 and refuses them until then (the feature `Your program as a node`, declared `Unsupported`; the row of the coverage page says `✔ 0.2`).
- **`Workload` is an enum of `UdpCbr` and `Command`.** One list `workloads` holds both, as the sketch had it, and a `kind` picks the keys. The two structs do not carry a `kind` field (it is the variant); they are written and described through private mirrors that add it, so the code of a user reads `UdpCbr { id, from, to, .. }` and the file and the schema have `kind` where they always had. The reader is by hand for the reason of `Loss` (D-049): the derived reader for a tagged enum reports an error in a value at the start of the mapping. The check of missing keys and of keys that belong to the other kind runs before it, from one table for both tagged types (the loss and the workload) that a test compares with the variants in the JSON Schema. The API breaks (`feat!`): `Workload` was a struct.
- **`run` is a list, without a shell.** The program and its arguments are separate texts, so there is nothing to quote, and a space or a `;` in a value cannot become another command. A string for a shell would be shorter to write and is the usual cause of injection; a scenario that needs a shell writes `["sh", "-c", "..."]` and says so. Limits are part of the format (256 entries, 4096 bytes each, 64 variables, no NUL character), so the readers and the fuzz targets (D-053) have a bound.
- **One placeholder, `{node.addr}`, checked when the file is read.** The node must exist, with a hint; any other text in braces is refused instead of passed on unchanged, which would run a program with the text `{server.address}` in its arguments. Braces that mean braces are written twice. More placeholders (the address on a named link, the port of a workload) can be added without breaking a file, because today everything else is refused.
- **`ready` has five ways and no default wait.** `udp-port`, `tcp-port`, `stdout-line`, `file` and `delay`; exactly one. Every way except `delay` needs `within`, because a program that never becomes ready must fail the run after a time that the file states, and a hidden default would be a time nobody chose. `delay` takes no `within` (it is the wait). No `ready` means ready when started, which is the right thing for a client that does not listen. The name is `stdout-line` and it matches by containing the text.
- **The stop is called `shutdown`.** The sketch said `stop: { signal, within }`, but `stop` of a `udp-cbr` workload is a moment (D-025's window), and one key with two shapes would make the reader and the schema guess. `shutdown` has `signal` (`TERM`, `INT`, `HUP`, `QUIT`, `USR1`, `USR2`; `KILL` is what follows, not a choice) and `within`, both with defaults that the documentation names (`TERM`, `5s`).
- **No window and no working directory in the file.** A program runs from the start of the run to its end; a `start` and a `stop` for it have no use before the metrics of a program (PRB-08) and can be added later. It runs in the directory of the scenario file (D-041); a key for another directory can be added later.
- **Left for the supervisor of programs:** the supervisor (start, readiness probes from `/proc/<holder>/net/{udp,tcp}`, the process group, `TERM` then `KILL`, the output into files cut at the limit of D-026, the limit for the length of a line that S14 asked for), the substitution of the placeholders in the backend, and the variables `NETSCENARIO_*`. Until then no `command` reaches the run, and `run.rs` works on the `udp-cbr` workloads only.
