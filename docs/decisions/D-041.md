# D-041: A program of your own is a node's workload of kind `command`, and the file says so

Accepted (2026-10-31); the details of the probes are settled by the spike S14. `kind: command` is the only way for a scenario to run code. It runs in the namespace of its node, as the invoking user (inside a user namespace that is uid 0 mapped to the user), in the directory of the scenario file, with `NETSCENARIO_*` in the environment (the addresses of the nodes, the directory of the run), and `{node.addr}` replaced in `run`. Readiness: a UDP or TCP port (read from `/proc/net/udp` and `/proc/net/tcp` of its namespace, since a UDP port cannot be probed by connecting), a line on standard output, a file, a fixed delay. Stop: `TERM`, then `KILL` after the time in the file; output goes to files of the run directory, cut at the limit of D-026; the exit code or the signal is in the result. Metrics: lines of JSON on standard output, read into the result; a malformed line is reported and not swallowed. A document says what it means to run a scenario that you did not write (SECURITY.md). Alternatives: probing by connecting (not possible for UDP); running the program outside the namespace (then it is not in the network).

**Settled by the spike S14 (2026-10-31, `spikes/s14_program.py`).**
- *Probes work from outside.* `/proc/<pid of the holder>/net/udp` and `.../tcp` show the sockets of the namespace of the node, and the supervisor can read them without entering it. A bound UDP socket has state `07`, a listening TCP socket `0A`; a socket bound to `0.0.0.0` and one bound to the address of the node are both found. Polled every 5 ms the probe saw a port within one polling interval of the bind on all three machines (p99 at most 7.5 ms, mostly 5 ms; the p50 depends on how the poll and the bind line up and was between 0.4 and 4.6 ms), with no false "ready" for 80 unused ports on each. A canary shows that a port bound in the namespace of the supervisor does not count in the node.
- *As whom.* A program started through `nsenter --net=...` keeps the environment and the working directory it was given, sees uid 0 and gid 0, and a file it creates belongs to the invoking user outside the namespace (uid 1000 where the user was 1000). The text above holds as written.
- *Stop.* The supervisor kills the one process that it started. A program that started a child leaves the child running until the end of the run (checked: the child was still there after the kill). The program therefore gets a process group of its own (`Command::process_group(0)`, safe), `TERM` goes to the group, and `KILL` follows after the time of the file: a program that ignores `TERM` and its child were gone after 0.5 s. A program that obeys `TERM` ends in under a millisecond with the signal as its status, which is what the result reports.
- *Output.* A reader that keeps the first megabyte and drains the rest takes 3 GB/s, so a program that prints without pause is never blocked or killed for it. The reader of release 0.1 (`read_until` for a line) has **no limit for the length of a line**: a program that prints without a newline made the reader hold 2 GB in one second. Release 0.2 limits a line (the rest of it is dropped and counted) and writes the output to files of the run directory, cut at the limit of D-026, before `kind: command` can be used.
