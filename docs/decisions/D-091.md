# D-091: A trace is a model whose rows come from a file, and a rate that changes is a class of `htb` that is changed

Accepted (2026-11-06). Release 0.3 adds trace-driven links (LMD-03). D-090 made models a source of events of the timeline and reserved `kind: trace`; D-083 says how a file reaches the scenario; D-079 chose `htb` for a rate that changes. This decision fills in the rest.

- **A trace is `model: { kind: trace }` with a source for each direction.** `forward`, `reverse` or `both` (never `both` with the others) name a `file`; each direction has its own trace and its own period, because the two traces of a Mahimahi pair differ in length. The rows are changes of the link: from the moment of a row until the next, the link has the row's rate, delay and loss. A column that the file does not have is not written by the trace and stays what the link says. `begin` moves the trace; `repeat` (default `true`, as Mahimahi plays its traces) begins it again, or, `false`, gives the link back as the file writes it when the trace is over. The rows are read once, when the scenario is loaded, and written into the scenario with the SHA-256 of the file (D-083); the run compiles them into `set` events like any other model, a row that changes nothing makes no step, and the bounds of D-090 (10,000 events for a link) are the bound of a trace. A trace with more rows than that is refused, and the message says the window that would make it fit.
- **Two formats.** *CSV*: a header with `time` and any of `rate`, `delay`, `loss`, a row for each change, every value with its unit (`500ms,5mbit,40ms,0.1%`); the trace lasts `period`, or, left out, until the last row has lasted as long as the row before it. A `rate` of `0` is a row in which nothing is delivered. *Mahimahi*: a line for each opportunity to deliver a packet, the time in whole milliseconds; the trace lasts until its last line. The opportunities in each `window` (default 100 ms, a whole number of milliseconds) give the rate of the window: the count times 1,514 bytes (an IP packet of 1,500 bytes and the Ethernet header, which is what the shapers count, D-079) over the width of the window. The file is a CSV only if its name says so (`.csv`); a Mahimahi trace has no usual extension, so `format: mahimahi` is written.
- **A rate that changes is a class of `htb` that is changed.** A direction whose rate changes during the run (a step, a state of a model, a row of a trace) is built through the fabric like one with a `queue`, with a `fifo` of the length that `netem` gave it (1,000 packets) if the file says none. The tree is planned from every state it goes through (D-059): the stages that a later state needs exist from the start, and a step changes only the parts whose values differ, each written whole (D-048), and never the leaf, so the queue keeps what it holds. A rate step is `class change` (the tokens are kept), a loss, duplication or corruption step is the `netem` of the node, and a delay, jitter or reordering step is the `netem` of the fabric port. An outage is a blackout `netem` behind the delay on that port (D-064). This replaces the `netem` rate for steps of the timeline too: a `netem` rate does not follow a change (D-070), and one machinery for the timeline, the models and the traces is easier to hold exact than two.
- **What the shaper follows, measured (S19, kernels 6.8 and 7.0).** The bytes that leave against rate times time: 0.4 % short at steps of 100 ms, 2 % short at 20 ms, 17 % at 5 ms, 41 % at 2 ms. So the rate steps are three features of the ledger: `rate-steps` (exact at 100 ms and more), `fast-rate-steps` (closer than 100 ms and not closer than 20 ms: limited), `very-fast-rate-steps` (closer than 20 ms: refused, with the window to use). They are known from the file alone, without a seed (a Markov chain by its mean stays).
- **A shaper cannot stop.** A packet that is in service when the rate drops to a few bits keeps the cost it was given at the old rate: with a floor of 8 kbit a packet waited a second after the rate had returned (measured here). So a row of rate 0 is not a tiny rate. It is the rate at which one frame is delivered in the row, and the feature `stalled-link` is limited: the scenario must accept it. A backend that can hold a link still (the Engine, release 0.4) declares it exact.
- **The delivery is by the byte.** A Mahimahi opportunity delivers one packet whatever its size; the shaper delivers the bytes of the window. Packets of the size of the opportunity (1,472 bytes of UDP payload) see the same link; smaller ones see more packets than Mahimahi would deliver. COVERAGE.md says so.

Alternatives: a trace as a list of states in the `periodic` model with the rows in the file (the two directions of a pair have periods of their own); a Mahimahi window of 1 ms (the Kernel backend does not follow it, the rate would be 12 mbit steps) or a window chosen by the tool (the trace would mean different things on different backends); a rate floor for a stall (the packet at the head waits for the old cost, measured); a `netem` rate for the steps (D-070); `tbf` (refills its bucket at every change, 27 % too many bytes at 20 ms); the rows kept in the file and read at the run (D-083).
