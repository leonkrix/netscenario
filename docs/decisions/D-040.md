# D-040: A corrupted packet is dropped by the receiver; the result tells it apart from a lost one, exactly for the node and by sequence where the packet allows it

Accepted (2026-10-31) and revised twice the same day, after the spikes S12 and S13b; the maintainer has to confirm the revision. The first version assumed that a corrupted packet is delivered (the UDP checksum would not be verified on a veth pair) and asked for a CRC-32 in every packet. The second counted the drops from `/proc/net/snmp`. Both were wrong or incomplete.

**What was measured.** With `corrupt 10%` no packet arrived with a corrupted payload (0 of 20,000, at 64, 200 and 1,200 bytes): the receiver drops it on a bad checksum, as a real network does. With the UDP checksum switched off by the sender (`SO_NO_CHECK`) the payload arrives corrupted (6.0, 8.2 and 9.6 percent, the same on both runner images). That is the share of payload bytes in a frame of 14 + 20 + 8 + payload bytes (6.0, 8.3 and 9.7 percent); a first prediction without the 14 bytes of the Ethernet header was too high, and the match is what shows that the header is among the bytes that can be hit. The counters of IP and UDP in `/proc/net/snmp` explained only 8.4 of the 9.3 percent that vanished at 64 bytes: `netem` flips a bit in a random byte of the whole frame, the Ethernet header included, and a frame whose destination address was hit is dropped by the interface with **no counter at all** (the raw socket marks such frames as meant for another host: 105 of 20,000 at 64 bytes, 48 at 200, 9 at 1,200). So those counters cannot be the method.

**What does add up** (S13b, 20,000 packets each; the interface counter, a raw socket in the receiving node and the UDP socket):
- *Lost in the queue* = packets sent minus the frames that the receiving interface counted (`/proc/net/dev`, read before and after, as ENV-07 reads the queue). The counter was exact in every run.
- *Corrupted and dropped* = the frames that the interface counted minus the datagrams that reached the sockets. Exact for the node, without a raw socket, and it includes the frames with a damaged address.
- *By sequence number:* a raw socket in the receiving agent (D-047) sees every frame that reaches the interface, also those the stack drops. A sequence that was seen on the wire and not delivered was corrupted. This named 94 percent of the corrupted packets at 64 bytes (1,686 of 1,783), 97 percent at 200 bytes (1,825 of 1,884) and 99.3 percent at 1,200 bytes (1,913 of 1,927). The others are counted but cannot be named, because the bit hit their header or the sequence number itself. The runner images gave the same (94, 97 and 99.7 percent). The second run on the runners added the full count: of 20,000 packets with `corrupt 10%` at 64 bytes the interface counted 20,000, the sockets delivered 18,180 and 18,193, the raw socket named 1,685 and 1,668 by sequence and 106 had a damaged header, so 29 and 33 packets (0.15 percent) were neither delivered nor nameable although their header was readable, probably a damaged sequence number. The implementation reports them as `dropped_corrupted` without a name, so `delivered + dropped_corrupted + lost_in_queue` equals the sent count exactly even though `corrupted_seq` is a lower bound. The figures are an upper bound by up to 0.2 points: a bit in the sequence number can make a number that was sent, so the implementation names a packet only if the magic, the flow and the range of the sequence agree, and counts the rest as unnamed. A packet that is neither delivered nor seen is lost in the queue.

**The decision.**
- *The default is the faithful one.* A workload keeps the UDP checksum on, a corrupted packet is a lost packet to the program, and `lost` counts it. The result adds, for each receiving node, `lost_in_queue` and `dropped_corrupted` (the arithmetic above), and where a scenario has corruption the receiving agent also runs the raw socket and the result names the corrupted sequences (`corrupted_seq`), with the count of those that cannot be named. The numbers are for a direction with one workload in it, the condition of D-038; with several the node-level figures stay exact and the naming is by sequence number, which each workload has.
- *A workload may switch the UDP checksum off* (`udp-checksum: off` on `udp-cbr`, spelled `udp-checksum: false` since D-056, for programs that accept a corrupted payload: media with error concealment, UDP-Lite-like uses). Then the packet gets a CRC-32 (wire format version 2, `docs/AGENT.md`; the formats are version 0, so this is allowed), the receiver counts `corrupted`, and no raw socket is needed.
- *Not taken:* a CRC-32 in every packet (it measures something that never happens with the checksum on, and `corrupted: 0` would read as "no corruption"); the counters of `snmp` (incomplete); treating corrupted packets as plain loss without saying so (the tool exists to say what happened to each packet).

Alternatives: sending with the checksum off by default (the program under test would no longer see what a real network does).
