# D-029: Fidelity is measured against bounds with reasons, one test at a time, and what the measurements found is documented before it is decided

Accepted. The cases, the bounds and the findings are in [FIDELITY.md](../FIDELITY.md); the tests are in `crates/netscenario-backend-kernel/tests/fidelity.rs`.

- **A bound is a number and a reason.** Physics gives exact lower bounds for delays; noise only makes packets later, so upper bounds leave room (0.5 ms for a median); counts and means get four standard deviations; a mechanism that is known gets its predicted number, with the bound around it. A test that cannot say why its bound is where it is does not have a bound.
- **A single packet is never judged.** The largest delay failed on a runner because one packet of 6,000 was 2.8 ms late. The 99th percentile replaces it (sixty packets would have to be disturbed). The smallest delay stays, because noise cannot lower it.
- **Judging is one function, and it is tested against wrong networks.** `judge` is used by the cases and by the canaries: a rate, a delay and a loss that are not applied must fail the case that expects them. A test of `judge` with made-up numbers shows that each wrong number is named.
- **The tests run alone** (`.config/nextest.toml`, `threads-required = "num-cpus"` for the fidelity binary), because the sender spins and two of them side by side on four cores disturb each other. Measured: 70 seconds for the 12 tests, the same on four cores and with four busy loops competing.
- **The report is generated.** Each case writes its part to `target/tmp/fidelity/`; `just fidelity` (`UPDATE_FIDELITY=1`) puts them into the block of `docs/FIDELITY.md` between the markers. The CI uploads the parts of each runner as an artifact (`fidelity-<os>-rust-<version>`), so the table can be compared per image. The committed block is from the development machine.
- **Three findings about `netem`, documented in COVERAGE.md:** the rate counts Ethernet frames (payload + 42 bytes); jitter reorders packets when it is larger than the gap between them (58 % to 72 % in the cases), and the results count them (`reordered`); and one `netem` qdisc with both a jitter and a rate cuts the jitter off (a mean of 42.7 ms for a configured 41.0, a deviation of 4.1 ms for a configured 5). The third was settled in D-030: the backend now builds that combination from two qdiscs, and the case measures 41.06 ms and 5.01 ms.

Alternatives: bounds as a percentage of the expected value (a delay of 20 ms and a loss of 5 % have different kinds of noise), measuring on an idle machine only (the CI is where the tests run), running the cases in parallel (faster, and unreliable), a JSON report assembled by a script (one more tool; the test already knows the numbers).
