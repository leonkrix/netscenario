# D-047: Packet capture is done by the agent with `recvmsg` on an `AF_PACKET` socket, and it checks itself against the counter of the interface

Accepted (2026-10-31, after the spike S13, `spikes/rust-capture/`), for release 0.2. The capture runs in a program of the node (the agent, D-025) and needs no tool on the machine.

- **How.** A raw packet socket in the namespace of the node, bound to the interface (`SO_BINDTODEVICE`), with the kernel's own timestamp of every frame (`SO_TIMESTAMPNS`), read frame by frame with `recvmsg`, written as a pcap with nanosecond timestamps. It is built with `nix` and needs no `unsafe` in our code (`rustix` 1.1.6 has no address type for `AF_PACKET`, no timestamps in the control messages and no `SO_BINDTODEVICE`). `tcpdump` reads the file without a warning and counts the same packets as its own capture of the same traffic (40,000), and the timestamps of the same packet are **identical** to the nanosecond in both files (they are the stamp of the kernel). The stamp is the real-time clock; the records of the agent use `CLOCK_MONOTONIC`, so the agent samples both clocks at the start of the capture and the result states the offset.
- **What the capture shows.** What the interface *sent* is what is left after the impairments, because the tap sits after the queue: with `loss 50%` and 5,000 packets the capture on the sending interface showed 2,430 packets and the one on the receiving interface 2,430. A packet that the queue dropped is in no capture. The pcap shows what the network delivered; what the program sent is in the records of its agent. The documents say so (PRB-09).
- **How complete it is, and what decides it.** The buffer of the socket is limited by `net.core.rmem_max`, because a larger one needs `CAP_NET_ADMIN` in the first user namespace, and the machines differ. On this machine (Debian 13, 212,992 bytes, 425,984 effective) nothing was lost up to 100,000 packets per second (200 byte payload, one thread, the idle machine); at 200,000 packets per second 0.003 to 0.3 percent of the frames were missing and at 300,000 0.16 percent; with every processor busy at 50,000 packets per second 0.02 to 0.6 percent. On the runner images (1,048,576 bytes, 2,097,152 effective) **no frame was lost** at 200,000 packets per second or with all four processors busy at 50,000. So the agent reads back the size that it got, the result states it, and the doctor shows `rmem_max`. The statistics that the kernel keeps for the socket (`PACKET_STATISTICS`) cannot be read through `rustix` or `nix`. So the capture **compares its count with the counter of the interface** (`/proc/net/dev` of the node, read before and after): the counter was exact in every run (300,000, 600,000 and 900,000 frames, against 300,000, 599,830 and 898,560 captured), and a capture with fewer frames than the interface counted is marked incomplete in the result, with the number that is missing. No capture is silently incomplete.
- **For the user.** `tcpdump` in a user namespace fails to read a file because it wants to change to the user `tcpdump`; `-Z root` is the answer, and the document on captures says so. On the Ubuntu 22.04 runner (tcpdump 4.99.1) `tcpdump` cannot run in a user namespace at all, not even to read a file: it fails with "Couldn't change to 'root'" because it cannot drop its rights there (`-Z root` does not help); 24.04 (4.99.4) works and counted the same 40,000 packets as ours, with timestamps identical to the nanosecond. The cause is the old `tcpdump`, not our file. The document on captures says that on Ubuntu 22.04 a pcap is read outside the user namespace (the workflow now does this and counts the packets there), and that capturing with `tcpdump` inside a node needs a newer `tcpdump` or real root.

Alternatives: a ring buffer (`PACKET_RX_RING`, TPACKET_V3), which has no limit from `rmem_max`, counts its own drops and would remove the loss above 100,000 packets per second; it needs `mmap` and therefore `unsafe`, so it would live in a small crate of its own with an audit (like the engine and the bindings), and it is the next step if the figures above are not enough in practice; the payload of a test stream is a few hundred packets per second, and a loss that is always detected is not a silent one. `tcpdump` or `dumpcap` as a program (a tool that the machine may not have, and its version decides the format).
