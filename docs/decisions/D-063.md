# D-063: The changes of a link go through a `tc` that lives for the run

Accepted (2026-11-02). It carries out the part of D-038 that D-062 left out. A change of a link used to start two processes, `nsenter` and then `tc` (2 ms, 3.6 ms on a busy machine), and a packet at a barrier waits for exactly that. A step is now done by one `tc -force -batch -` for each node, started through `nsenter` when the direction is built and kept until the teardown.

- **The acknowledgement is an error on purpose.** `tc` talks to the kernel for each line and waits for the answer before it reads the next, so when the line after a change is done, the change is in the kernel. That line is a `qdisc show` of a device that does not exist, which `tc` answers with `Cannot find device "ack<n>"` on its standard error, the stream that also carries the errors of the lines before it; `-force` makes `tc` go on after a line that failed. S11 used a `qdisc show dev <interface>` on the standard output instead, and that does not hold for the real use: `tc` keeps the filter of the last `show` between the lines of a batch, so the output named other interfaces and had one line or two for the same queues (measured on the way, `tc` 6.15). The mark is short because `tc` cuts a device name at 15 characters: the first version had a longer one, all its marks came out the same, and the first test run said at once (through the note below) that no batch answered.
- **Every way it can fail is covered.** A line that `tc` refuses is the answer to the change, as for a process, with what `tc` said. A batch that does not answer within two seconds, that ends, or that cannot be written to is ended, and the change is made with a `tc` process (the change is the whole state, so doing it again is the same as doing it once); the node keeps using processes after that, and the result says so (`notes`). A batch that cannot be started or does not answer when asked once at the start is the same, before the run depends on it. Two seconds is a hang and not a busy machine (a change took up to 2 ms with every processor busy) and is far below the 10 seconds a sender waits at a barrier. S11 saw one batch that did not answer on a runner; its cause was not found, and the first suspect (the buffering of the standard output of `tc`) does not apply to the standard error.
- **The result gets `notes`.** `Backend::notes` (a method with a default, so no backend breaks) is asked once, before the teardown, and the sentences go into the new field `notes` of the result, on the command line (`note:`) and in Python (`result.notes`). A new field does not change the version of the result. It is for facts about how the run was done, not for errors: here, that a change was made the slow way. The run is just as exact then, only slower, which `events` shows as well.
- **Measured** (this machine, Debian 13, `tc` 6.15, the rate step of the test of the timeline, three runs): a step takes 0.22 to 0.44 ms from the call of the run to the answer of the backend, including the request to the supervisor, against about 2 ms with processes. The 0.03 ms of S11 is the batch alone. The packet at the barrier waited about 1 microsecond in two runs and 1.05 ms in one.
- **Tested.** The states of a direction go from every state to every state through the batch (121 and 144 pairs) and are those of a fresh queue every time, and the run has no note. A batch that is stopped with `SIGSTOP` (what a hang looks like from outside) is replaced: the change takes the two seconds of the limit and then gives the same queues as a fresh one, the stopped process is gone, the next changes do not wait, and there is one note. The protocol has tests against a stand-in for `tc`: success, a refused line and the lines after it, the tail line that `tc` prints after a failure, a batch that does not answer, ends, or is not there, a line break in a line, and a canary in which an error before the acknowledgement must not be taken for success.
- **Not done.** One batch for each node, not for each interface: lines of different interfaces go through the same one (tested with two links). The request to the supervisor still costs about 0.2 ms; a second channel for changes would save that and is not worth a protocol of its own.

Alternatives: the `qdisc show dev <interface>` of S11 (does not hold, see above); a pipe of `tc` per interface (more processes, no gain); the netlink interface (D-009 keeps `tc` for 0.2; it would remove the process and the parsing of the acknowledgement together and is the way if the Kernel backend ever outgrows `tc`); no fallback and an error if the batch fails (a run that fails because of a tool that has a slower, exact way is worse than a note).
