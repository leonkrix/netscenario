# Decisions

A log of the decisions that are hard to undo, with the reasons and the alternatives. Add an entry before building on a decision. To change one, add a new entry that supersedes it; do not edit history.

Status: **accepted**, **proposed** (to be confirmed by an experiment or a first implementation), **superseded**.

## D-001: The name is netscenario

Accepted. Descriptive, like the sibling projects, and free on PyPI and crates.io when checked. Components: the Rust crates `netscenario-*`, the command `netscenario`, the Python package `netscenario`, the pytest plugin `pytest-netscenario`.
Alternatives: netweather (memorable, says less), wirelab (sounds like hardware).

## D-002: Rust core with a Python layer

Accepted. The semantics live in one place, in Rust: a static binary for the command line and the agents, precise timers and a fast packet path for the later engine, the same language as the planned Tetrys library, and use from `cargo test`. Python (PyO3 bindings built with maturin, plus a pytest plugin) is how most people will use it.
Alternatives: Python only (faster start, but a weak base for a packet-level engine and for the agents), Go (good network libraries, no other reason).

## D-003: Dual license, Apache-2.0 or MIT

Accepted. Open source, the convention in the Rust ecosystem. Apache-2.0 adds an explicit patent grant, which matters for networking code; MIT keeps it simple for those who prefer it. The same for all crates and Python packages.
Alternatives: MIT only (as the Playwright guards), copyleft licenses (would limit use in company test suites, which are the main users).

## D-004: One repository for the framework; the Tetrys library lives elsewhere

Accepted. Crates, bindings and plugin are released together and share a version history, and maturin expects the Python package next to the crate. The Tetrys library is independent (it should be usable without this framework) and later becomes an example and a test subject here.

## D-005: The kernel is the reference, and backends declare their fidelity

Accepted. The Linux kernel network stack is the ground truth. Every backend publishes what it reproduces faithfully ([COVERAGE.md](COVERAGE.md)). A scenario that asks for more is refused with an error and never approximated silently. Limited features need an explicit `allow-limited`. Other backends are checked against the kernel with differential tests.

## D-006: Linux first

Accepted. The real emulation needs Linux. The development happens on Linux. Windows and macOS are served by the portable proxy backend, with honest limits.

## D-007: The scenario format is versioned YAML with a generated JSON Schema

Proposed (confirm with the first implementation). Readable, diffable, familiar. The schema is generated from the Rust types so that code and documentation cannot drift. Values have strict units. Scenarios are data and cannot run code except through an explicit `command` workload.
Alternatives: TOML (worse for nested time lines), a Python DSL only (ties the format to one language), a custom language (cost without benefit).

## D-008: Traffic and measurement come from agents inside the nodes

Accepted (confirmed by the sender and receiver of spike S8, see D-016). A small static Rust binary runs inside every node, so scenarios do not depend on tools installed in the node (iperf and so on) and per-packet records have one format. Your own programs are measured through their output and through packet captures.

## D-009: Call `ip` and `tc` first, netlink later

Accepted (confirmed by spike S7, see D-014). Getting a first, correct kernel backend is worth more than a native implementation. The calls sit behind the backend interface and are replaced by netlink in 0.4 (BKD-05).
Alternative: netlink from the start with `rtnetlink` or `nlink` (better in the end, slower to a first result).

## D-010: Two Python distributions

Accepted (confirmed by spike S9, see D-014). `netscenario` (bindings, API, statistics) and `pytest-netscenario` (the plugin, which depends on it). This follows the naming convention of pytest plugins and lets the API be used without pytest.

## D-011: The feature ledger and the coverage matrix drive the work

Accepted. `FEATURES.md` and `docs/COVERAGE.md` are the plan that is visible to everybody. A pull request moves lines forward; a feature that is not in the ledger is not planned. A release has acceptance criteria and is not made until they hold.

## D-012: Working practice follows the sibling projects

Accepted. Pull requests into a protected `main`, squash merge, a single required check `CI passed`, Conventional Commits, all actions pinned to commits, releases by tag with provenance and staged approval, documentation written as part of the change. The maintainer's working documents stay local and are listed in `.gitignore`; nothing in the repository refers to them.

## D-013: Findings of the spikes S1 to S6 decide the Kernel backend of release 0.1

Accepted. Measured on Debian 13 (kernel 6.12, iproute2 6.15), on the GitHub runners (Ubuntu 22.04 with kernel 6.8, Ubuntu 24.04 with kernel 7.0) and in Docker; the scripts are in [spikes/](../spikes/README.md) and the consequences are in [COVERAGE.md](COVERAGE.md).

- **Rootless stays in 0.1 (BKD-02).** Unprivileged user namespaces work by default on Debian 13 and Ubuntu 22.04, and on Ubuntu 24.04 after one setting. The tool does not hide the restriction: `doctor` and the error message name what failed, why, and the three ways out (user namespaces, root, capabilities), and the permissions guide (CIX-04) belongs to 0.1. In a container the rootless way needs `SYS_ADMIN` and a seccomp profile that allows `unshare`; this is documented, not worked around.
- **Reproducible loss is limited, not promised without conditions.** `netem ... seed` exists from iproute2 6.6.0 on and gives the same loss pattern in a quiet namespace (checked in 7 runs on each of three machines and across kernels 6.8, 6.12 and 7.0). The pattern depends on the packets that enter the queue, so the Kernel backend uses quiet namespaces, checks the packet counter of the queue, and marks a run that is not reproducible. The coverage cell is `~` until a test of the framework proves it. The `doctor` checks that the installed `tc` knows `seed`.
- **Judging tests use percentiles, never the maximum, and never a minimum from the tail of a distribution.** One packet in about 2000 arrives roughly 2 ms late, and the tables of `netem` are cut at about 3.5 to 4 sigma. The numerical tolerances of QA-06 are set when measurements from the CI runners exist, which are noisier than a development machine.
- **`ip` and `tc` are looked up in `PATH` plus `/usr/sbin` and `/sbin`** (on Debian they are not in the `PATH` of a normal user), and `doctor` prints where it looked.

Alternatives: dropping rootless from 0.1 (would leave the main CI case, an unprivileged user, to the later engine); promising reproducible loss on the Kernel backend without conditions (would be false as soon as a stray packet enters the queue).

## D-014: The spikes S7 to S10 confirm D-009 and D-010, fix the Rust version, and show what the engine still has to solve

Accepted. Measured on Debian 13 (kernel 6.12, Ryzen 7 5800X) in unprivileged user namespaces; the experiments are in [spikes/](../spikes/README.md).

- **D-009 holds: the Kernel backend of 0.1 calls `ip` and `tc`.** Netlink works (spike S7): with `nlink` 0.33.0 the namespaces, the veth pair, the addresses and every `netem` setting that was tried give the same qdisc as the `tc` command line, and `netem seed` gives exactly the loss pattern that `tc` gives. A change of a running `netem` takes 12 microseconds through netlink and through `tc -batch`, against 1.1 ms for one `tc` process per change, so the speed is no reason to hurry. What speaks against netlink now is the library: `rtnetlink` cannot configure `netem` at all (`netlink-packet-route` 0.33.0 knows only `fq_codel` and `ingress`), and `nlink` is ten months old, has one maintainer, changes its API between minor versions and contains `unsafe` code. The calls stay behind the backend interface, and netlink replaces them with BKD-05. Candidates then: `nlink` pinned to an exact version, or our own thin layer for the `netem` options on `netlink-packet-core` and `netlink-sys`. Decide at BKD-05 with the maturity of `nlink` at that time. Either way, a fidelity test must measure the jitter distributions, because `tc qdisc show` does not print the distribution table, and the distribution tables of iproute2 (`/usr/lib/tc/*.dist`) are a run-time dependency of `nlink` unless we embed them.
- **D-010 holds: two Python distributions, built with maturin, abi3.** One wheel (`cp39-abi3`, 256 KB) serves several Python versions; the plugin as a second distribution with a `pytest11` entry point is found by pytest; the interpreter lock can be released while Rust works. Release wheels are built in a manylinux container, not on the development machine, whose tag (`manylinux_2_34`) is too new for older systems. The lowest supported Python version is still to be chosen (3.10 is the system Python of Ubuntu 22.04).
- **Minimum supported Rust version: 1.85 for release 0.1**, with a CI job on exactly that version next to stable. It is what `pyo3` 0.30 and `tokio` need, and it allows edition 2024. If `nlink` is adopted it becomes 1.88. Both CI images have Rust 1.99.1 (spike S10).
- **The userspace engine (BKD-06) is feasible and keeps its place in 0.4.** One thread on AF_PACKET sockets forwarded 100,000 packets per second with a fixed delay of 20 ms and no loss using about 44 percent of one core, and with a seed it drops exactly the same packets in every run. The timer decides the accuracy: `epoll_pwait2` is exact at high rates but 0.3 to 0.7 ms late at 10,000 to 50,000 packets per second (the core sleeps between packets), a spinning loop is exact at the price of a whole core, and `epoll_wait` with milliseconds is too coarse. Open before the design of 0.4: jitter needs a sorted queue, not a FIFO; frames from a veth pair carry unfinished checksums (offload), so a TCP workload needs the engine to complete them, to switch the offload off, or to use a TAP device (which an unprivileged user can create in a user namespace); batching with `recvmmsg` and `sendmmsg`; many flows; bit rates with full-size frames.

Alternatives: netlink from the start (a first Kernel backend would depend on an immature library), a scratch-built netlink layer now (cost without a need), a lower MSRV (it would exclude the current `pyo3`).

## D-015: The run on the CI runners confirms S7 to S9 and qualifies the timer finding of S8

Accepted. The `Spikes` workflow ran S7 to S10 on `ubuntu-22.04` (kernel 6.8, 4 virtual CPUs, AMD EPYC) and `ubuntu-24.04` (kernel 7.0), as the runner user.

- **S7 and S9 gave the same results as on the development machine.** `nlink` made the same qdiscs as `tc` in all ten comparisons, and its seed 1234 gave the same 200-packet loss pattern even with the old `tc` of the images (5.15, 6.1.0), which only reads the result. A change of a running `netem` took 16 to 18 microseconds. The abi3 wheel built and the five tests passed with Python 3.10 and 3.12. Together with spike S2 the complete loss patterns of two seeds are now identical on three machines, kernels 6.8, 6.12 and 7.0.
- **The engine of S8 forwarded 100,000 packets per second on both runners** with no loss and with the delay within 0.04 ms (p99) with `epoll_pwait2` and `spin`, using 3 seconds of CPU in 6 (about half a core). At 150,000 packets per second without delay the 22.04 runner shows the first strain (p99 0.4 ms, p99.9 2.3 ms), so about 150,000 small packets per second is a practical ceiling on a 4-CPU runner for this simple loop. The seeded loss was identical on both kernels and in both runs (3,971 of 40,000 packets for seed 7), and another seed gave another set.
- **The timer finding of D-014 was specific to the development machine.** There, `epoll_pwait2` was 0.3 to 0.7 ms late (p99) at 10,000 to 50,000 packets per second; on the runners it was within 0.2 ms. How late a sleeping core wakes depends on the processor and its idle states, so the engine must report its timer precision per run (ENV-05) and never promise a fixed figure. `spin` stays the most exact choice at the price of a whole core; `epoll_wait` with milliseconds stays too coarse (up to 1 ms late at low rates).
- **The image lists were right about the tools and slightly off about the compiler:** both images have Rust 1.99.1, rustup 1.29.2, clippy and rustfmt; the system Python is 3.10.12 and 3.12.3; gcc is 11.4.0 and 13.3.0; glibc is 2.35 and 2.39; Docker 28.0.4. The wheel is tagged `manylinux_2_34` on both images and on the development machine (glibc 2.41), because the tag follows the symbols that the build links against; wheels for older systems need a build in a manylinux container.
- **The corrected spike runs show failures honestly:** on `ubuntu-24.04` with the default settings the runner reports 5 FAIL (S1.1 and S2.0 to S5.0, no namespace can be created), where before the fix only S1.1 was reported and S2 to S5 recorded nothing at all.

## D-016: D-008 is accepted; D-007 stays proposed until the first implementation

Accepted. The phase of the spikes ends with D-008 accepted and D-007 open on purpose.

- **D-008 (agents inside the nodes) holds.** The sender and the receiver of spike S8 are small Rust programs that run inside a node, put a sequence number and the send time into every packet, and record the arrival time. At 100,000 packets per second they measured the one-way delay of a direct veth pair as 2 microseconds on average (p99 3 microseconds) on the development machine and 4 to 5 microseconds on the CI runners, with no packet lost, and a delay of 20 ms through the engine within 0.04 ms (p99). No tool had to be installed in the node. Not yet checked: that the agent is a static binary (musl) that the supervisor can start by path in any node, the documented wire format, and the delivery of the binary next to the command line; these were built for release 0.1 ([AGENT.md](AGENT.md)).
- **D-007 (versioned YAML with a generated JSON Schema) stays proposed.** No experiment can show whether the format is good; the first implementation of the model (SCN-01 to SCN-04) and the tests of its error messages will. The decision is confirmed or replaced when the model of release 0.1 is finished.

Alternatives: accepting D-007 now (would record a decision that nothing has tested), leaving D-008 proposed (the measurement it waited for exists).

## D-017: The lowest supported Python is 3.11, and the rule is the oldest version that has not reached its end of life

Accepted. Python 3.9 reached its end of life on 2025-10-31 and 3.10 on 2026-10-01, so release 0.1 starts at **3.11** (end of life 2027-10), built as one `abi3` wheel (`abi3-py311`) that also serves the newer versions. The system Python of Ubuntu 22.04 (3.10) is no reason to go lower: the CI installs the Python it needs, and users of that system can use `uv` or another installer. The rule for later releases is that the lowest supported version is the oldest one that has not reached its end of life when the release is made; raising it is allowed in a minor release before 1.0 and is written in the changelog. The `abi3-py39` setting of spike S9 was a trial and is not carried over.

Alternatives: 3.10 (already past its end of life), 3.12 (a longer window, but it would leave out users who still run 3.11 for no gain).

## D-018: The Python side uses uv, maturin, hatchling, ruff and pyright in strict mode

Accepted. The tools of the Python packages are chosen for the strictness of the checks and for one reproducible environment, and they are cheap to change while there is little code.

- **uv** manages the environment as a workspace of the two packages (D-010) with one lock file, `uv.lock`, which is committed. It also fetches the lowest supported Python (3.11, D-017) for `just py-test-min`.
- **maturin** builds `netscenario`, the package with the native module from `crates/netscenario-py`; its version is the one of the Rust workspace, so the crates, the bindings and the plugin are released together (D-004). The `extension-module` feature of PyO3 is not set in `Cargo.toml` but by maturin, so that `cargo test` still links. **hatchling** builds the plugin, which is pure Python; a test checks that both packages have the same version.
- **ruff** formats and lints (security, annotations, docstrings in the Google style, naming, bugbear, simplifications, pytest style).
- **pyright in strict mode** checks the types, with `py.typed` and a stub for the native module. It is chosen over mypy because it is faster, strict mode is its normal way of working, and it is the checker that most editors use. The cost is that the PyPI package fetches a Node runtime on first use; this is no problem on a development machine or a CI runner. mypy would be the choice for a build without network access.
- **The tests of the plugin** run pytest inside pytest (`pytester`), and each check that judges has a canary that must fail.

The wheels that `uv build` makes on the development machine carry the platform tag of that machine (`linux_x86_64`). Release wheels are built in a manylinux container (REL-01, PYT-08).

Alternatives: mypy (the long-standing standard, slower, strict mode is a collection of flags), pip with venv and a requirements file (no lock for the workspace), setuptools for the plugin (works, was used in spike S9, but hatchling needs no `setup.py` history).

## D-019: The bindings are built as an extension module without a Python interpreter, and the crate has no Rust tests

Accepted. The first CI run failed on Ubuntu 22.04: its system Python is 3.10, and PyO3 looks for `python3` even for an `abi3` build and refuses an interpreter below the minimum that `abi3-py311` implies (3.11). The same would have hit every developer on that system. `.cargo/config.toml` now sets `PYO3_NO_PYTHON` and `PYO3_BUILD_EXTENSION_MODULE` as defaults, so that cargo neither looks for nor links a Python interpreter; maturin gives PyO3 its own configuration when it builds the wheel and is not affected. An extension module cannot be linked into a test program without Python, so `netscenario-py` has `test = false` and is covered by the Python tests in `python/`. This replaces the statement in D-018 that maturin alone sets the extension-module mode.

Alternatives: install Python 3.11 in the CI (fixes the CI but not the developer on Ubuntu 22.04), the `extension-module` feature in `Cargo.toml` (still needs the environment variable to avoid the interpreter search, and the feature is being replaced by the environment variable in PyO3).

## D-020: The scenario format of release 0.1, the YAML parser serde-saphyr, and Rust 1.89

Accepted. The research is from 2026-10-30 (crates.io, GitHub, RustSec) and a prototype that read faulty files.

- **The format of release 0.1 is the contract in [SCENARIO-FORMAT.md](SCENARIO-FORMAT.md).** Its rules: strict (unknown and duplicate keys are errors); one spelling per thing; units are lower case and stuck to the number; probabilities only with `%`; rates and sizes decimal, with `kib`, `mib`, `gib` for powers of 1,024; values must be whole numbers of the smallest unit; a value that cannot be applied exactly is refused, not rounded (a jitter that reaches below zero, more than 100,000 packets per second); anchors, aliases, merge keys and tags are refused; the keys of later releases are reserved and say in which release they arrive; `version: 0` until 1.0, and version 0 may change in any minor release. D-007 stays proposed until the model is implemented and this contract has met real files.
- **The parser is `serde-saphyr` 2.** It is written in Rust with `unsafe` forbidden, fuzzed and designed not to panic on malformed input, reads YAML 1.2 (so `no` stays the text "no"), rejects duplicate keys, limits the size of the input, is actively maintained (last change 2026-10-28) and is MIT or Apache-2.0. Every error of the prototype carried the line, the column and the source line with a mark: unknown unit, number without unit, misspelled key with the list of the expected keys, wrong type, duplicate key, broken indentation. Its tree of 40 crates (with serde and schemars) passes `deny.toml`. It gives no logical path for syntax errors, so the path of an error of content comes from our own validation, which keeps the position of every value. The rendering of errors in colour belongs to the command line, not to the model crate.
- **Rejected:** `serde_yaml` (archived), `serde_yml` (archived, RUSTSEC-2025-0068, unsound), `serde_yaml_ng` and `serde_norway` (built on `unsafe-libyaml`, RUSTSEC-2024-0449, unmaintained), `serde_yaml_bw` (hardly used).
- **The lowest supported Rust is 1.89** (D-014 said 1.85; the rest of D-014 stands). `serde-saphyr` needs 1.89. This affects only people who build the crates with an older Rust from their distribution; wheels, binaries and `rustup` users are not affected, and the CI runs 1.99. The version is changed in `Cargo.toml`, the `justfile`, the CI matrix, the README and the contributing guide.
- **The tools of the model** are `schemars` 1 for the JSON Schema (and a test that fails when the committed schema differs from the generated one), `thiserror` for the error types, `insta` for snapshots of the error messages, `proptest` for the round trip from value to text and back, a corpus of faulty files with their expected messages, and our own parsers for the units: `humantime` and `bytesize` accept more spellings than this format allows, and their messages could not be made to name the file.

Alternatives: TOML (D-007 considered it), a parser with an older Rust (an unmaintained foundation), a format with relaxed units (`0.02` as a probability), which would make the same file mean different things to different readers.

## D-021: The model has one set of types, and the positions in the file come from a second reading with the parser

Accepted. The scenario types are the file, the program interface, the builder and the schema in one: they read and write the format, `schemars` describes them, and the checks of the contents work on them whether they came from a file or from code. What a type cannot say is lost on the way from a file: where a value stood. The YAML library reports the position of an error it finds itself but not of a value that it read correctly, and a check of the contents (a node that does not exist) needs that. Wrapping every field in a type that carries its position (`Spanned`) would have given the model a second shape that every new field has to repeat in three places (the wrapped type, the conversion, the writer).

Instead, `source.rs` reads the file a second time with `granit-parser`, the parser that `serde-saphyr` is built on, and notes the position and the length of every key and value under its path (`topology.links[0].between[1]`). The checks of the contents report paths, and the position is looked up by path; a builder gives the same paths without positions. The same pass finds what the format refuses in YAML itself (anchors, aliases, tags, merge keys, nesting deeper than 32 levels), the keys and values of later releases, and the keys that a mapping lacks, each reported at the place that it concerns. The cost is a direct dependency on `granit-parser` (MIT or Apache-2.0, the same version that `serde-saphyr` brings), and the file is parsed twice, which a file of at most 1 MiB makes irrelevant. A test compares the table of required keys with the required keys of the generated schema, so the table cannot drift from the types; a snapshot test with 50 faulty files holds the messages and runs identically in every run.

Alternatives: `Spanned` wrappers in the model (rejected, see above), the validation interface of `serde-saphyr` with `garde` or `validator` (more dependencies, and its paths are mapped back to the file by fuzzy matching), no positions for errors of the contents (the path alone is much harder to use in a long file).


## D-022: A run lives in a PID namespace with the supervisor as its first process, and the supervisor is a child process

Accepted. A run needs a cleanup guarantee that does not depend on the supervisor being able to clean up (BKD-04). Named objects (`ip netns add`, bind mounts) need an exit handler and a `clean` command, and both fail when the process is killed. Instead the run happens inside a PID namespace (`unshare --user --map-root-user --mount --pid --fork --kill-child --mount-proc`, or without the user namespace as root) in which the supervisor is the first process. The nodes are network namespaces held by small processes (`unshare --net` with a program that waits) and addressed by their process id (`ip link set ... netns <pid>`, `nsenter --net`). When the supervisor dies, even by `kill -9`, the kernel ends every process in the namespace, and a network namespace that no process holds is removed with them. Checked on the development machine: in such a namespace the first process has the id 1, and a network namespace can be created and configured in it.

- **The supervisor is a child process** (the same binary with an internal subcommand, started through `unshare`), never a thread of the caller. A process with several threads, such as Python with the bindings, cannot move itself into a new user namespace, and the workspace forbids `unsafe`. The caller talks to the child through a pipe. The command line and the Python package use the same structure.
- **The backend depends on the tools** `unshare` and `nsenter` (util-linux), `ip` and `tc` (iproute2), as D-009 says for the last two. `doctor` checks them.
- **`netscenario clean` is a safety net, not the mechanism.** With no named objects there is nothing to find by name in the normal case. The command looks for processes of a run that lost its supervisor (a run started by an older version, or outside a PID namespace), and a test covers it (D-024). This replaces "finds leftovers by name prefix" in the plan.
- **Crash tests** let the supervisor die at every step of the setup and the teardown (`NETSCENARIO_FAIL_AT=<step>`, only in test builds), then check that no process of the run is left and that the next run works, as root and unprivileged.
- **Limits and watchdog (SAF-02, SAF-03):** at most 8 namespaces in a run (release 0.1 needs 2), a maximum run time of the duration of the scenario plus 60 seconds (an option changes the margin), and the watchdog sits in the outer process so that it works when the supervisor hangs. The memory limit of agents comes with the agent and uses `prlimit` because cgroups need rights that the unprivileged mode does not have.

- **What building it settled** (the second change of the Kernel backend): (1) The supervisor is also in a *network namespace of its own* (`unshare --net`), and at start it refuses to run unless it is process 1 and sees only `lo` (SAF-01). Started in the namespace of the host it does nothing, which a test proves. (2) A node is a network namespace held by a process of the same binary (`hold`) that switches IPv6 off for the new interfaces and says when it is ready; it needs no `sleep` of the system. (3) The failpoints of the crash tests are compiled in all builds and do nothing unless `NETSCENARIO_FAIL_AT` is set: a feature flag would let `cargo test` run no crash tests. (4) `teardown()` reports success when the supervisor died before it could answer, because the kernel has then done what the teardown is for; a death anywhere else is an error that says what the supervisor wrote on its standard error (an `unshare` that is refused says so there, and the message names the AppArmor case). (5) The watchdog kills the `unshare` process of the run; `--kill-child` and the PID namespace end the rest. (6) The links use `10.100.n.0/30` (`.1` the first node of `between`, `.2` the second), fixed MAC addresses and fixed neighbour entries, so that no ARP packet shifts the loss pattern. (7) A direction's `netem` sits on the interface of its sender. (8) `netem` is given `limit` and microsecond times: a time that is not a whole number of microseconds is refused before anything is created (`Backend::check_values`), and the queue limit is derived (see `docs/COVERAGE.md`, "Queue of the Kernel backend before 0.3"). (9) The seed of a direction is derived from the seed of the scenario (`derive_seed`, SplitMix64 mixing), and the values are pinned by a test because a change would give old seeds new patterns.
- **Not done yet:** nothing of what this entry listed (the memory limit of programs is D-026, the result format with `seed`, `drawn` and `loss_reproducible` is D-027). Closed after this entry: the root code path is tested (locally as root in a user namespace, on the CI with `sudo`), the tools answer in English (`LC_ALL=C`) because the hints look for their words, and a scenario without `seed` gets a drawn one (D-023).

Alternatives: named namespaces with `ip netns add` and an exit handler (a `kill -9` leaves them behind), cgroups for the cleanup (not available without rights), a library for `unshare` and `setns` such as `nix` in the caller (does not work in a process with threads), a root daemon (against the principle of working without root).

## D-023: A backend declares its capabilities as data, and what depends on the machine is part of the declaration

Accepted. `netscenario-core` defines the interface of a backend (`Backend`), the list of features (`Feature`, one per row of `docs/COVERAGE.md`) and `Capabilities`: for each feature `Exact`, `Limited` (with the restriction) or `Unsupported` (with the reason and the way out). `check` derives the features a scenario needs, each with the first path where it asks for it, and compares them with the declaration. It lists everything that is refused, before anything is created; `provision` calls it first, and tears the backend down if a later step fails. `Limited` is refused unless the scenario accepts it (`allow-limited`, release 0.3), and an accepted restriction is returned so that the result can record it.

- **A declaration depends on the machine.** The Kernel backend builds its declaration from an `Environment` (the version of `tc`). With a `tc` older than iproute2 6.6.0 the feature "same seed, same loss pattern" is `Unsupported`, with the way out: a newer iproute2, leaving out `seed`, or the Engine backend. Where the scenario does not write a `seed`, it asks for no reproducibility and the run is allowed; the result will record that the loss is not reproducible (RPT-01). Refusing every scenario with loss on a stock Ubuntu would be too hard, and recording what happened is not a silent approximation.
- **A scenario without a `seed` gets a drawn one** (`provision`), if the backend can apply a seed, so that every run can be repeated; the seed is part of what `provision` returns, for the result. If the backend cannot, the scenario runs and `loss_reproducible` is `false` for one with loss. This replaces the first wording above ("the result will record that the loss is not reproducible") with what the code does. The seed of a direction is `derive_seed(seed, link, direction)` and only directions with loss get one.
- **The page and the code are compared by a test.** Each feature has the label of its row; the test reads `docs/COVERAGE.md`, and a feature that is `Exact` on a complete machine must be a `✔ 0.1` in the Kernel column. The cell of "same seed, same loss pattern" therefore changed from `~ 0.1` to `✔ 0.1 (needs iproute2 6.6.0 or newer)`: a `~` would make every seeded scenario fail without `allow-limited`, and the restriction (the pattern depends on the number of packets in the queue) is handled by quiet namespaces and a packet counter that marks a run as not reproducible if it was disturbed.
- **Capability errors show the path, and the line when the text is at hand.** `Display` shows `= path: seed`. `CapabilityError::render(name, text)` gives the form of the errors of reading a file, with the line and a mark, through `netscenario_model::Error::in_source`, which looks up the positions of the paths (D-021). The command line will use it.
- **The interface is small and grows.** Waiting for programs and streaming records arrive with the agent, packet capture with release 0.2.

Alternatives: a trait method `supports(feature)` that every backend implements by hand (no table to compare with the page), refusing every `Limited` feature forever (no way to accept a known restriction), a version check in the scenario reader (the model has no access to the machine, by design).

## D-024: `doctor` probes with the commands of a run, and `clean` ends only holders without a supervisor

Accepted. `netscenario doctor` (ENV-04) and `netscenario clean` (BKD-04) are described for people in [DOCTOR.md](DOCTOR.md).

- **The probe uses the real commands.** Whether a run can get its namespaces is not guessed from the user id or from a list of known settings: `doctor` runs the `unshare` command of a run (same flags) once with `--user --map-root-user` and once without, and a small script inside tries a virtual Ethernet pair and three `netem` commands (delay, loss and rate; the distribution `normal`; a `seed`). The probe lives in the namespaces it creates and leaves nothing behind (a test compares the interfaces of the host before and after). The settings of the system (`kernel.apparmor_restrict_unprivileged_userns`, `kernel.unprivileged_userns_clone`, `user.max_user_namespaces`, container markers) are read only to choose the words of the fix when the probe fails.
- **Looking and judging are separate** (`inspect` and `assess`). The judging takes plain findings, so every broken machine (AppArmor, a container, no `netem`, an old `tc`, missing tables) is tested with findings instead of with a machine that is broken in that way.
- **Exit codes.** 0 if no check failed, 3 (environment) otherwise. A warning means a limit that the line names (an old `tc` without `seed`, missing tables); it does not fail, because scenarios without that feature run. Of the two ways to get rights only one has to work; the other is `info`.
- **`seed` needs both the version and the probe.** The declaration of the backend decides by the version of `tc` (D-023); the doctor adds the probe and warns when either says no (an old `tc`, or a new enough one that the kernel refuses).
- **`clean` ends nothing it cannot recognise.** A process counts only if its program name starts with `netscenario` and its arguments are exactly `hold <run id>` or `supervise <run id> <nodes>` with a run id of the form `<pid>-<counter>-<nanoseconds>`. A run with a living supervisor is never touched, even if its caller is gone; the supervisor ends such a run itself when its input closes. `--dry-run` reports only.
- **Found by the CI before this existed:** a `tc` built from source looks for `normal.dist` in `/usr/lib/tc`, which is empty on Ubuntu 24.04; the CI sets `TC_LIB_DIR`. The check `tables` reports it.

Alternatives: deciding the rights from the user id and a table of distributions (wrong for containers and for every new restriction, and untested), probing in the namespace of the host (against SAF-01), `clean` by name prefix of namespaces (nothing is named, D-022), `clean` that also ends runs whose caller is gone (a supervisor that is waiting on a slow caller would be killed).

## D-025: The agent reads CLOCK_MONOTONIC through rustix, counts payload, and records in a binary file

Accepted (the three choices were put to the maintainer on 2026-10-30 and taken as proposed). The agent is described in [AGENT.md](AGENT.md).

- **The clock is `CLOCK_MONOTONIC`, read through `rustix`.** Sender and receiver are different processes in different namespaces on one machine, so they must read the same clock, and it must not jump when the time is adjusted. `rustix` offers `clock_gettime` and the socket options as a safe interface, so no crate of ours needs `unsafe` (the spike S8 used `libc` with `unsafe`). The wall clock (`SystemTime`) was rejected because an NTP step in the middle of a run would falsify delays without a sign.
- **`packet-size` is the UDP payload.** As in `iperf`. The rate counts payload bits, so the packets per second are `rate / (size × 8)`. The headers of IPv4 and UDP (28 bytes) come on top on the wire; the largest payload without fragmentation is 1472 (MTU 1500). The model already refused sizes outside 16 to 1472 and rates over 100,000 packets per second.
- **The record file is binary, JSON Lines is an export.** 24 bytes per packet (sequence, send time, receive time), a documented header, a parser that refuses a cut-off file. The run computes statistics from it and writes JSON Lines only on request. Alternative: JSON Lines straight from the receiver (one format, but about three times the size and slower in the receiver at high rates).
- **The sequence number on the wire has 32 bits** to fit the header of 16 bytes that the model announced. The sender refuses a stream that would wrap it (about 11.9 hours at 100,000 packets per second) instead of wrapping it.
- **The sender spins for the last stretch before each packet** (150 microseconds) and so uses a core. A sleep alone wakes up tens of microseconds late, which would show as a gap in every result. The summary reports the largest lateness.
- **The agent is not static in the Kernel backend.** The nodes there share the file system of the host. The musl build comes with the release.
- **The agent is a separate program, started by path, and speaks JSON lines on standard output**; the types of these lines are shared with the starting side, so they cannot drift apart. It resolves no units.

Alternatives: `libc` with `unsafe` in the agent crate (as the spike; more control over socket options, but unsafe code in the project for two calls), the wall clock, the clock of the supervisor passed in packets (needs a handshake), `SO_TIMESTAMPNS` for the receive time (more exact by a few microseconds, needs control messages; later if QA-06 shows it matters).

## D-026: A program in a node is read through the supervisor by polling, and its memory is limited with prlimit

Accepted. The agent runs as a program of a node (D-025), so the backend needs more than "start": the output of the agent is its report, its input is how it is told to stop, and its end is a result (BKD-03, WRK-01, SAF-02).

- **Three calls in the interface** (`netscenario-core`): `start_program` (as before, now with `Program::memory_limit`), `poll_program(program, wait)` and `send_line(program, line)`. `poll_program` returns as soon as a program wrote a line or ended, or after `wait` with an empty answer, and gives the new lines, the exit (`Code` or `Signal`), the end of standard error (16 KiB) and a `truncated` mark. Polling and not a callback or a stream, because the supervisor answers one request at a time, the caller waits on one program at a time (a run is sequential: receiver ready, sender ends, receiver stopped), and a blocking call with a timeout is the simplest thing that cannot lose a line.
- **Nothing is lost at the end.** A program is reported as ended only after its standard output and standard error have been read to the end (at most 500 ms of grace for a program that left a process behind that keeps the pipe open). Two tests found that this was first not so: the end of a supervisor and the end of a program were reported before the thread that reads standard error had finished (a flaky hint in an error, and a flaky `stderr` in the state). Both are fixed and run 30 times in a row.
- **The supervisor keeps at most 10,000 lines per program** and says when it dropped some (`truncated`). The agent prints a handful.
- **Memory is limited with `prlimit --as=BYTES`** (util-linux, which the backend needs anyway), as `nsenter ... prlimit --as=N -- program`: `prlimit` sets the limit and becomes the program, so nothing stays in between. A limit on the address space is a limit on what a program can map, not on what it uses, and that is the point: allocating past it fails. Alternatives: cgroups (need rights that the unprivileged mode lacks, as D-022 said), `ulimit` in a shell wrapper (a shell in between, and not every program is started by a shell), `RLIMIT_AS` set by the supervisor on itself (would limit the supervisor too).
- **`prlimit` is a required tool** (`Toolbox`, `doctor`), like `unshare` and `nsenter`.
- **The end-to-end test needs the agent binary** next to the supervisor binary. `just test` and `just test-kernel` build it (the recipe tests both packages); a test that does not find it says so and stops, except on the CI, where it fails.

## D-027: The result format of release 0.1, how a run is ordered, and what the statistics mean

Accepted. The format is described field by field in [RESULTS.md](RESULTS.md).

- **One directory, one JSON result, raw records beside it.** `result.json` (versioned: `format` and `version`, 0 until 1.0), the binary records of each workload (D-025), and on request one JSON Lines file with a line for each packet. The result holds everything a reader needs to judge it: the provenance (version of netscenario, time, backend and its details, kernel, processor), the seed with `drawn` and `loss_reproducible`, the accepted restrictions, the addresses and a fingerprint of the scenario. No host name, user name or path, because a result may be shared.
- **The fingerprint is SHA-256 of the canonical JSON of the scenario**, so comments and layout of the file do not matter and any value does. SHA-256 is written out in the crate (forty lines, the published test vectors, a million-letter case), not taken from `sha2`: a fingerprint protects nothing, and one dependency less is worth more than the convenience. The tests pin the output, so the crate can replace it at any time.
- **The order of a run** (`netscenario_core::run`): provision, start every receiver and wait for `ready`, fix one moment 500 ms ahead and start every sender with it (so the workloads start together and a slow start of a process does not shift one of them), wait for the senders, wait the `settle` time for the packets in the network, tell the receivers to stop, read the records, tear down, compute and write. The network is torn down on every path, and the first error is the one returned. A workload with `start` and `stop` is a sender with a later moment and a shorter duration.
- **`settle` is a fixed wait, not a drain detection.** A receiver cannot tell a packet that was lost from one that is still in the network, so the run waits one second plus twice the longest hold of the scenario (largest delay plus four times the largest jitter). A packet that needs longer counts as lost, and the result says how long the run waited (`timing.settle_ns`). A rate limit that builds a queue longer than that is not covered by the default; the `settle` option exists (open: the command line, and a default that knows the queue, see PLAN 12a).
- **Statistics are plain and stated exactly.** Loss is `lost / sent` with `lost = sent - distinct packets that arrived`. Delay percentiles are the nearest rank (always a measured delay). Throughput is the payload that arrived in each second, counted from the first packet sent, not scaled. A duplicate counts once and not in the delays; a sequence number that was never sent is counted as `unexpected` and not as received. Each rule has a test with numbers worked out by hand, and canaries that fail on wrong data.
- **The backend tells the run its addresses and itself.** Two methods of the interface: `address(link, end)` (the Kernel backend computes `10.100.n.1/.2` on the caller's side, with the function the supervisor uses) and `describe()` (name and details such as the version of `tc` and how the rights were obtained).
- **The tests of the run are of two kinds.** With a fake backend that plays the agent: order, arguments, failure paths and the teardown on each. In real namespaces with the real agent: the delay of the link, a window of a workload, two workloads in opposite directions, the loss pattern of a seed (same seed, same lost packets, another seed other ones) and a run that cannot start.
- **Not in this change:** the command `netscenario run` and `validate` (CLI-01), which find the agent next to the program (`agent_next_to`) and the supervisor in the same program; round trip time (PRB-03); reordering (PRB-04).

Alternatives: a JSON result with all packets inside (too large), CSV (no types, no versions), a hash from the `sha2` crate, a drain detection by watching the receiver go idle (cannot tell idle from lost, and a slow queue looks idle), starting the senders one after the other as soon as each is ready (the workloads would not start together).

## D-028: The command line of release 0.1: one program that is also its own supervisor, and what each exit code means

Accepted. The commands and options are in [CLI.md](CLI.md).

- **`run`, `validate`, `schema`, `doctor`, `clean`.** `run` is `netscenario_core::run` with the Kernel backend (D-027); `validate` reads and checks a file and says what the scenario needs; `schema` prints the JSON Schema. `--json` on `run`, `validate`, `doctor` and `clean` makes standard output JSON and nothing else.
- **The program is its own supervisor** (D-022): a run starts `netscenario supervise ...` and `netscenario hold ...` inside its namespaces. `main` answers these two before the command line is read; they are not in the help. `clean` recognises these processes by the name of the program (`netscenario...`), which this satisfies. The agent is a second program that belongs next to it (`netscenario_core::agent_next_to`), and `run` says where it looked when it is missing.
- **Exit codes.** A scenario that is wrong, and a scenario that the backend cannot reproduce exactly, are both 2: both are about what the file asks for, and the capability error already names the feature, the backend and the way out. A backend that cannot be started (a tool or a permission missing, namespaces refused) is 3, with a line that points to `doctor`. A run that failed after it started is 4. 1 is reserved for a failed assertion and no command returns it yet.
- **A run does not overwrite another.** Without `--out` the result goes to `netscenario-results/<name>-<UTC time>/`. `--seed` replaces the seed of the file, which is how a run that drew its own seed is repeated; the summary prints the flag to use.
- **The summary is for people, `result.json` is for machines.** The summary shows the seed (and warns when the loss cannot be repeated), the packets, the delay and the throughput; for a run longer than six seconds it shows the average throughput and leaves the per-second series to the file, because fifty numbers in a row cannot be read.
- **Problems are shown the same way everywhere.** A faulty file, a refused capability and the JSON of `validate` use the same rendering and the same fields (line, column, path, help) as the model.
- **Tests run the real program.** `tests/binary.rs` starts the binary: a run in namespaces, `--json`, `--seed`, the default directory, a faulty file, a refusal by the backend, a program without its agent, the supervisor refusing to run on the host, and `validate`. Tests that need namespaces or the agent stop where the machine cannot, and fail on the CI.

Alternatives: a separate binary for the supervisor (two programs to install and keep in step), a command per backend (`run` chooses by the `backend:` key), the exit code 3 for a capability refusal (it mixes "your machine" with "your file" and loses the line of the file), printing the whole throughput series (unreadable for a long run).

## D-029: Fidelity is measured against bounds with reasons, one test at a time, and what the measurements found is documented before it is decided

Accepted. The cases, the bounds and the findings are in [FIDELITY.md](FIDELITY.md); the tests are in `crates/netscenario-backend-kernel/tests/fidelity.rs`.

- **A bound is a number and a reason.** Physics gives exact lower bounds for delays; noise only makes packets later, so upper bounds leave room (0.5 ms for a median); counts and means get four standard deviations; a mechanism that is known gets its predicted number, with the bound around it. A test that cannot say why its bound is where it is does not have a bound.
- **A single packet is never judged.** The largest delay failed on a runner because one packet of 6,000 was 2.8 ms late. The 99th percentile replaces it (sixty packets would have to be disturbed). The smallest delay stays, because noise cannot lower it.
- **Judging is one function, and it is tested against wrong networks.** `judge` is used by the cases and by the canaries: a rate, a delay and a loss that are not applied must fail the case that expects them. A test of `judge` with made-up numbers shows that each wrong number is named.
- **The tests run alone** (`.config/nextest.toml`, `threads-required = "num-cpus"` for the fidelity binary), because the sender spins and two of them side by side on four cores disturb each other. Measured: 70 seconds for the 12 tests, the same on four cores and with four busy loops competing.
- **The report is generated.** Each case writes its part to `target/tmp/fidelity/`; `just fidelity` (`UPDATE_FIDELITY=1`) puts them into the block of `docs/FIDELITY.md` between the markers. The CI uploads the parts of each runner as an artifact (`fidelity-<os>-rust-<version>`), so the table can be compared per image. The committed block is from the development machine.
- **Three findings about `netem`, documented in COVERAGE.md:** the rate counts Ethernet frames (payload + 42 bytes); jitter reorders packets when it is larger than the gap between them (58 % to 72 % in the cases), and the results count them (`reordered`); and one `netem` qdisc with both a jitter and a rate cuts the jitter off (a mean of 42.7 ms for a configured 41.0, a deviation of 4.1 ms for a configured 5). The third was settled in D-030: the backend now builds that combination from two qdiscs, and the case measures 41.06 ms and 5.01 ms.

Alternatives: bounds as a percentage of the expected value (a delay of 20 ms and a loss of 5 % have different kinds of noise), measuring on an idle machine only (the CI is where the tests run), running the cases in parallel (faster, and unreliable), a JSON report assembled by a script (one more tool; the test already knows the numbers).

## D-030: A direction is built in the order of its stages (loss, rate, delay with jitter), with two qdiscs where one cannot do it

Accepted. The question was what to do with a scenario that has a jitter and a rate in one direction, which one `netem` qdisc reproduces wrongly (D-029). The answer follows from what the scenario means and from what the kernel can do.

- **What the scenario means is now written down** (`docs/SCENARIO-FORMAT.md`, "Impairments of a direction"): the stages of a direction act as loss, then rate, then delay with jitter, whatever order the keys have. Packets wait for the rate in a queue, in order; each then travels for its own delay; a jitter larger than the gap between packets lets one overtake another. The format said "has this standard deviation" for a normal jitter and said nothing about the order of the stages, so the measured 4.1 ms was a violation of the first sentence and an accident of the second.
- **The four ways out, in the order of the project's rules.** (1) *A notice in the result*: runs the scenario without the author's consent to a result that does not match the numbers, and a notice does not make an approximation any less one. This breaks "a backend never approximates silently" in spirit; rejected. (2) *Refusing the combination*: honest, but it makes every typical link with a jitter and a rate impossible (a mobile link, a satellite hop, a Wi-Fi access: two of the four examples), when the kernel can do it exactly. (3) *Counting it as limited (`~`) and waiting for `allow-limited`*: right for a limit that cannot be removed, and the machinery stays for the day there is one. Not right here, because this limit can be removed. (4) *Making the backend exact*: a prototype (a `netem` with the rate as the root and a `netem` with the delay and jitter as its child) measured 41.11 ms, 5.00 ms and 28.6 % reordered where one qdisc gave 42.71, 4.19 and 0 %; the model of the series gives 41.01, 4.99 and 28.8. **Chosen.** A backend refuses what it cannot do faithfully; this one can.
- **The build** (`netem.rs`): a direction with both a jitter and a rate gets a root qdisc with `limit 1000` (the queue of the link), the loss with its seed and the rate, and a child (`parent 1:1`) with the derived limit for the packets in flight, the delay and the jitter. The loss stays in front of the rate, where one qdisc has always applied it, so the seeded loss patterns do not change. Every other direction keeps its one qdisc, and everything that was measured about them stays as measured.
- **Proof.** The case in the fidelity suite, a canary that judges the numbers of the old behaviour with its bounds (all three fail) and the same canary with the new numbers (they pass), a model with both compositions, the unit tests of the argument builder, and a test of `tc qdisc show` that checks which stage holds what.
- **Not done, and why it matters later.** `apply` builds a direction once, at time zero. The changes over time (release 0.2) must remove the child when a step leaves a direction without a jitter or without a rate, because `tc qdisc replace` of the root keeps the child. A uniform jitter with a rate goes through the same code and is covered by the unit tests, but has no case of its own; the loss together with the two stages is not measured. They are listed in [FIDELITY.md](FIDELITY.md), "What is not measured yet".

Alternatives: a `tbf` as the rate stage (a token bucket with a burst of at least `rate / HZ`, so it does not serialise packet by packet, which the single-stage `rate` and the model do), a notice and an `allow-limited` for something that can be fixed, and a new `Feature` for the combination (it would turn a thing the backend does exactly into a thing it declares as limited).

## D-031: Python calls the core in the same process, and the core can be observed and cancelled

Accepted. The question was how `netscenario.run(...)` reaches the Rust core: by starting the command line as a child process and reading its JSON, or by calling the library through the bindings.

- **In the same process, through PyO3.** The reasons, in the order of their weight. (1) The main use of the Python layer is a test that builds a network, starts *its program* in a node, reads what the program writes and measures (the README, WRK-06 in release 0.2). That is a session on a live network: `start_program`, `poll_program`, `send_line`, `teardown`, which the library already offers through `Backend`. A one-shot command cannot express it, and a second protocol between Python and a long-running command would rebuild the library's interface. (2) Errors arrive as types: a `CapabilityError` with the feature, the path, the reason and the way out is an object that the pytest plugin can decide on (skip, fail, explain), not text on standard error. (3) Progress and cancellation belong to the library: a Rust user wants them as much as a Python user, and the command line gets a progress line from the same hook. (4) The command line and Python are then two thin shells over `netscenario_core`, not Python as a shell over the shell with exit codes and text in between.
- **What this costs, and the answer to each.** A blocking Rust call cannot be interrupted by Ctrl-C or by `pytest-timeout`: the core gets a **cancel token** that the waiting loops look at, and the binding runs the work on its own thread, gives up the GIL, and waits in slices of 100 ms that call `check_signals`; an interrupt sets the token, the run tears down and returns `Cancelled`. A panic of Rust becomes a Python exception (the workspace forbids `unsafe`); a crash of the process is possible in principle, but everything that touches the system runs in child processes that the kernel ends when the supervisor dies (D-022). Callbacks from Rust to Python take the GIL for the moment of the call.
- **Observing a run.** `RunOptions` gets an optional observer that is told the phases of a run (the network is built, the receivers are ready, the workloads have started with their duration, the progress once a second, the wait for the packets in the network, the collecting, the teardown). The command line uses it for a progress line when standard error is a terminal; Python passes a callable.
- **The binaries.** Python cannot be the supervisor of a run (it has several threads and cannot move into a user namespace, D-022), so the wheel carries the program `netscenario` (which is its own supervisor) and `netscenario-agent`, and the bindings tell the Kernel backend where they are. The same is true of the other design, so it does not decide anything.
- **Results are frozen dataclasses in SI units** (seconds, bit/s, ratios from 0 to 1) with the raw JSON beside them, typed for pyright in strict mode.
- **In four steps:** the observer and the cancel token in the core (and the progress line of the command line), the bindings and the Python API (model, builder, `run`, results, exceptions), the pytest plugin, the wheels (manylinux x86_64 and aarch64, an install test from the built wheel). The session API for programs under test comes with release 0.2 and needs no new design, only more of the same bindings.

Alternatives: the command line as a child process (the simplest, and the cleanest for a one-shot run, but a dead end for sessions, typed errors, progress and a second interface to keep in step), a long-running server process with an RPC protocol (the session API without the library, plus a protocol to version), and Python code that does the whole run itself (it would be a second implementation of the semantics, against D-002).

**What building it settled (D-031, step 3.8b).**

- **The exception classes are defined in Python and made from Rust by one factory.** `netscenario.errors.from_native(kind, message, details)` makes the instance; the native module hands it a kind, a message and plain tuples. The classes stay typed and documented in one place, and the native module knows nothing of them. A scenario built in code reports its problems by path only, because the lines of a generated text mean nothing.
- **The builder composes plain data and the core checks it.** The Python builder writes the same structure as the file and has no rules of its own; `build()` hands it to the model, so the rules cannot drift. A test shows that a built scenario and the file give equal canonical JSON.
- **A run is a thread, a slot and a wait in slices.** The core runs on its own thread; the calling thread waits on a condition in slices of 100 ms with the GIL given up and looks for signals between them (`check_signals`). An interrupt cancels the run, which tears down and returns, and then the `KeyboardInterrupt` is raised. An exception in the observer is kept, the run is cancelled, and the exception is raised afterwards. Tests: a cancel from a timer thread, `_thread.interrupt_main`, an observer that raises.
- **The scenario goes into the run as the text it was read from**, so that a refusal by the backend can show the line of the person's own file.
- **The two programs are found by `NETSCENARIO_BIN_DIR`, the package, or the checkout.** The wheel puts them in `netscenario/_bin`.
- **The Python tests run scenarios.** They stop where the machine cannot make namespaces (with the reason from `doctor`) and fail on the CI. The Python job of the CI prepares the runner as the Rust jobs do (a shared composite action: `tc` with the seed, the permission for user namespaces).

## D-032: The pytest plugin is a runner over `netscenario.run`, with a guard for the environment and plain asserts

Accepted. The plugin is described in [PYTEST.md](PYTEST.md).

- **A runner, not a second API.** The fixture `netscenario` gives a `Runner` that adds three things to `netscenario.run` and nothing else: scenario files are found next to the test (then in the ini directories, then in the root), every run goes into the temporary directory of the test, and the environment is checked. The semantics stay in the core and the Python package.
- **Assertions are plain `assert`.** A DSL for assertions would be a second language on top of Python. The numbers are floats in SI units, and a test says `assert media.delay.p99 < 0.150`. What a plain assert cannot do (confidence intervals, baselines, the `expect` section of the file) comes with the releases that bring the statistics (ASR-02 to ASR-07).
- **The guard has the rule of the project's own tests.** A machine that cannot run scenarios skips a test with the reason and the fix from `doctor`, but on a CI (`CI` is set) the test fails, because a test that never runs there proves nothing. `--netscenario-environment` overrides it either way. The machine is asked once per session and only when a test runs a scenario: a session that does not use the plugin pays nothing, and a test that only reads a scenario runs anywhere.
- **The numbers go where a CI can read them.** A section in the report of the test (shown on failure), and properties of the test in a JUnit file. The properties are set on the test item, as `record_property` does, because the JUnit file takes them from the last report of the test: the first version put them on the report of the call, where they were silently lost. A test that checks the JUnit file found it.
- **The marker has one argument and three options, and says what is wrong.** `@pytest.mark.netscenario("file.yaml", seed=, settle=, packets=)` with `netscenario_result` is the short form for a test that needs one result. A wrong marker is an error of the test with a message, not a silent default.

Alternatives: a fixture that returns the module (the skeleton; no gain over `import netscenario`), a custom assertion helper (see above), skipping on a CI too (hides a machine that was set up wrongly), and putting the properties on the call report (does not reach the JUnit file).

## D-033: One platform wheel carries the extension module, the supervisor and the agent, and the command

Accepted. How the wheels are made is in [PYTHON.md](PYTHON.md), "Installing".

- **One wheel per architecture, the stable ABI.** `cp311-abi3`, so one wheel serves every Python from 3.11 on (D-017); it is a platform wheel because of the programs in it. manylinux_2_28 (glibc 2.28: Debian 10, Ubuntu 20.04, RHEL 8 and everything newer) is the oldest platform that the target audience of CI runners and developer machines does not leave behind.
- **The programs are in the wheel, not downloaded and not built at install time.** A run needs the supervisor (the program is its own supervisor, D-022) and the agent, and Python cannot stand in for either (D-031). The wheel has them in `netscenario/_bin`, built in the same manylinux container as the extension module, so they link only to the C library of the old distribution. The files keep their execute permission (checked in the wheel). The alternative, a second package for the programs, would give a Python package that fails at its first run when the two versions do not match.
- **The command `netscenario` is a launcher.** `pip install` gives the command through an entry point that replaces the Python process with the bundled program (`os.execv`), so signals, exit codes and the terminal are the program's. `python -m netscenario` does the same. No Python stays in between.
- **The lookup is in the order of trust**: the environment variable, then the package, then a checkout of the repository. A wheel that lacks its programs does not borrow them from a checkout by accident (the smoke test installs into a clean environment and removing the programs makes it fail, which was tried).
- **Built on a runner of each architecture, natively.** The Arm wheel is built on a GitHub-hosted Arm runner in the aarch64 manylinux container, not cross-compiled or emulated: no emulation to be slow or wrong, and the install test then runs on the same architecture. The action that does this, `PyO3/maturin-action`, is pinned to a commit, as is the version of maturin (the action checks its checksum).
- **A wheel is tested where it is installed.** The job `wheel-test` takes the wheel from the build, makes a clean environment with `uv`, installs the wheel and the plugin, and runs `python/smoke/wheel_smoke.py` from outside the checkout with `python -I`: the package must come from `site-packages`, the programs from inside it, the command from the `bin` directory of the environment, `doctor` must say ok, a scenario must run through the installed package, and an inner `pytest` must run one through the installed plugin. It runs on Ubuntu 22.04 with Python 3.11, on 24.04 with 3.14, and on Arm with 3.12. The same script runs locally with `just wheel-smoke`.
- **Not in this step.** The upload to PyPI, signing and provenance of the wheels (REL-01 to REL-03), musllinux wheels, and a static agent. The wheel is tagged `linux` when built locally and manylinux when built by the CI.

Alternatives: `cibuildwheel` (a general tool for Python extensions, more than is needed for one module and two programs and it tests with pytest inside the container, which cannot create namespaces), cross-compiling or QEMU for Arm (slow and a source of errors that a native runner does not have), a source distribution only (every user would need Rust and the build of the programs), and a `data` directory of scripts instead of `_bin` (installs the programs outside the package, where the package cannot be sure to find its own).

## D-034: A release is a tag; one version for everything; the registries trust the workflow, and a maintainer approves

Accepted. The steps are in [RELEASING.md](RELEASING.md), the promises in [VERSIONING.md](VERSIONING.md).

- **One version for the five crates, the two Python packages and the programs in the wheel** (D-004). It is written once, in `Cargo.toml`; `python/release/version.py` writes the other places (the internal dependencies, the plugin and its exact pin on `netscenario`) and checks all of them, the lock files included, in the tests and in the release workflow. A pre-release is `0.1.0-rc.1` for Cargo and `0.1.0rc1` for Python; the script converts, and the release checks the names of the files. The plugin depends on exactly the same version, so a plugin never meets another package than the one it was tested with.
- **Five crates are published, the bindings are not.** `netscenario-model`, `-core`, `-backend-kernel`, `-agent` and `-cli` go to crates.io under their names (the command is still `netscenario`, `cargo install netscenario-cli netscenario-agent`); `netscenario-py` is `publish = false`, because it exists as the wheels. Every package carries the licence texts (copies, checked by a test) and the README of the repository. `cargo publish --workspace` orders the crates and builds each against the packages of the others; the CI does it as a dry run in every pull request.
- **The release is made from a tag, not from a branch.** The tag must be on `main`, name the version in the files, have a section in `CHANGELOG.md`, and its commit must have passed `CI passed`. The jobs then repeat nothing that the CI tested differently: the wheels come from the same reusable workflow (`wheels.yml`) that the CI calls, so what is published was built and installed the way the CI did.
- **No stored token.** crates.io and PyPI trust this workflow, each in an environment of its own (`crates-io` and `pypi`; trusted publishing, OIDC), so the job for one registry cannot ask for the token of the other; the PyPI upload makes attestations (PEP 740) for every file. The environments have the maintainer as a required reviewer, so nothing is published before a person looks at the finished run: there is no staging on either registry, and the approval is the staging. The two publishing jobs each need it, so the crates (immutable, cannot be undone) and the packages on PyPI are two decisions. The deployments link to the pages of the published versions. The publishing jobs use no cache and no artifact except the checked one.
- **The changelog is the titles of the pull requests** (Conventional Commits, squash merge), by git-cliff, written into the release pull request, where a person reads and edits it before it is merged. A title that is not conventional is shown under "Other", never dropped silently. The commits of the experiments before the workspace are left out.
- **Before 1.0 a minor release may break**, in the open: the title has `!`, the changelog says **Breaking**. The format versions stay 0 until 1.0.
- **First release by hand for crates.io only**: trusted publishing needs a crate that exists, so the names are taken with `0.0.0` and the versions yanked; PyPI has pending publishers and needs no placeholder. Only one pending publisher can exist for a repository, workflow and environment, so the second new project can be registered only after the first upload of the first; for the first release of this repository that meant a gap between the upload of the wheels and the upload of the plugin, and `0.1.0-rc.1` was published that way (two jobs, three approvals). With both projects in place the upload is one job again, wheels first and then the plugin, because the plugin pins exactly the wheels. The environments were renamed from `release` to `crates-io` and `pypi` after that release, and `0.1.0-rc.2` tested the change.
- **Not in 0.1**: static binaries, musllinux and macOS wheels, a source distribution of `netscenario`, signing of the GitHub release, an SBOM.

Alternatives: `release-plz` or `release-please` (a bot that opens the release pull request; more moving parts and a token that can push, and the review of the changelog is the part that matters), `cargo-release` (a local tool that publishes from the maintainer's machine, which needs a stored token), an API token in a secret (the thing trusted publishing removes), cibuildwheel (D-033).

## D-035: A run takes the way that `doctor` reports: its own rights if it has them and they work, else a user namespace

Accepted. The first version chose by the user id alone (root: own rights, anyone else: a user namespace), while `doctor` probed the rights of the process. A user who is not root but has `CAP_NET_ADMIN` and `CAP_SYS_ADMIN` passed the probe and still failed the run when user namespaces were refused (found while writing the permissions guide; reproduced with an unprivileged process with the two ambient capabilities and `user.max_user_namespaces=0`, which gave "No space left on device").

- **The rule.** The backend decides once, in `KernelBackend::new` (the Python package and the command line both pass through it). A process has rights of its own if its effective user id is 0 or its **ambient** set (`CapAmb` in `/proc/self/status`) holds the two capabilities. Such a process tries the namespaces of a run with its own rights (one `unshare ... true`, a few milliseconds), then in a user namespace, and takes the first that works; if neither works it keeps its own rights, so that the run fails with the answer of `unshare`. A process without rights of its own takes the user namespace without a probe. The result records the choice (`rights`).
- **Why the ambient set.** A run starts `unshare`, which starts the supervisor. A capability that is only permitted or effective (from `setcap` on the file, or from a process that was started with it) is dropped at the first `exec`; only the ambient set survives. `doctor` probes by running the same `unshare`, so it reports the truth, and a process with capabilities on the file is told `own rights` is not available.
- **Root without the rights.** Root in a container without `SYS_ADMIN` used to fail even where a user namespace works. It falls back to the user namespace now, as `doctor` already said.
- **How it is tested.** The decision is a function of the text of `/proc/<pid>/status` and of two probes, with canaries (one capability is not enough, an old kernel without `CapAmb`, the real user id and not the effective one). A test in the CI step that runs as root starts itself as an ordinary user with `setpriv --ambient-caps` and checks the way and that a node can be created; with one capability and with none it must choose the user namespace, and a check with a wrong expectation must fail.

Alternatives: raising the ambient capabilities from the program (needs `unsafe` for `prctl`, which the workspace forbids), a command line option for the way (the user would have to know what `doctor` already knows; `Mode` stays for the library), probing with the whole probe of `doctor` (it also builds a veth pair and three `netem` qdiscs: too much for the start of every run).

## D-036: A run counts the packets of each queue with loss and compares them with the packets of the workloads

Accepted. The pattern of lost packets of `netem` is a function of the seed **and of the number of packets that enter the queue**: each packet draws one number. The quiet namespaces (no IPv6, fixed neighbour entries, D-022) keep other packets out, and the patterns were identical on three machines, but a promise of "the same seed, the same lost packets" that the run cannot check would sometimes be false without saying so. ENV-07 was in the ledger for 0.1 and documents described it before it existed; this builds it.

- **What is counted.** After the senders have ended and the run has waited for the packets in the network, the backend reads the root queue of the interface of the sender of each direction that has random loss (`tc -j -s qdisc show`): the packets it sent on, dropped and still holds are the packets that entered it. A direction with a rate and a jitter has a second queue behind the root (D-030); the root draws the loss, so only the root is counted. The root has to be a `netem` queue, else the backend says so.
- **What it is compared with.** The packets that the senders of the workloads put into that direction: `packets` minus the ones the kernel refused (`errors`) in the summary of the agent. Directions without loss are not checked (their queue draws no number that matters), and a run without a seed is not checked (it is not repeatable anyway).
- **What it says.** `seed.queue_checks` lists each direction with `expected` and `counted`; if any differs, `loss_reproducible` is `false`, and the command line names the queue and both numbers. The result format stays at version 0: a field was added, and a reader that does not know it can ignore it.
- **A new method of the backend trait**, `queue_packets`, whose default says "cannot count" (`None`): a backend that cannot count leaves the result as it was. The Kernel backend answers through a new request to the supervisor.
- **How it is tested.** Parsing of the statistics with canaries (the child queue is not counted, no root, a root that is not `netem`, a missing field). In `core` with a fake backend: queues that agree, a packet too many, too few, one in the direction where nothing was sent, no counting, a direction without loss. In real namespaces: the count equals the 417 packets of the workload with one queue and with two, and a canary in which another program sends one more datagram from the node of the sender is found (`counted = expected + 1`).

Alternatives: reading the statistics of the receiving interface as well (it would also count what arrives, which the receivers already record), comparing in the agent (it cannot see the queue), and leaving `loss_reproducible` to the seed and the version of `tc` alone (the state before: a claim without a check).
